# E14.F2.S7 - supervision guarantees under `--runtime process` (process-mode cells)

Scope per the priority change: process mode first, owned Neo4j + Kafka test stack, **no Docker image built or used, Docker-mode cells deferred** (E14 closes them last). The product ran with `DOCKER_HOST=unix:///nonexistent/e14-no-docker.sock`; the only containers on the host were the owned `e14-*` Neo4j and Kafka (user-approved throwaway infrastructure, pinned image ids, memory-limited as in S4/S6).

## What changed

- `graph-loader stop --runtime process --recover [--run-dir DIR]` (new, `orchestrator/process_service.recover_registered`): for a run whose CLI died abruptly. Refused while the CLI is alive (`the run's CLI is still alive; use graph-loader stop (without --recover)`). Every registered child whose identity (pid + start time + boot id) still matches gets SIGTERM through its pidfd, SIGKILL after `grace` (15 s), and a `recovered` record is appended to the registry. The report names what was signalled, killed and still remaining and lists the retained attempt files (spill, plan, lock files); **nothing is ever deleted**. Exit 1 only if a process is still alive after the SIGKILL.
- Test infrastructure only: `tests/installed_service/process_support.py` (the S4 helpers moved out of `test_service_process_runtime.py`, which now imports them; its 14 cell ids are unchanged) plus `Fleet`, `kill_child`, `producing`, `mid_load`; `LiveStack(pin_neo_port=True)` (opt-in, `service_config["pin_neo_port"]`, default unchanged): Docker republishes Neo4j on a *new random loopback port* after a stop/start, and process-mode children receive `NEO4J_URI` once, so the outage cells publish Neo4j on a port chosen up front; `inspect_strict.group_offsets` passes the stack's prefix (it silently assumed `e09`).
- New cells (live, integration): `test_service_process_supervision.py` (11) and `test_service_process_ordering_dlq.py` (12). New unit tests: 3 in `test_process_service.py` (`recover` refused while alive; recover signals what a dead CLI left behind; escalation to SIGKILL when SIGTERM is ignored; second recovery is a no-op report).

## Cells and results (Linux host, Ubuntu 7.0.0-38, Python 3.12.3, installed non-editable wheel `sha256 814d11bc...a0ae6`)

Run 1 (kept, **red**): `logs/s7-run1.log` - 10 passed, **13 failed**, 952.67 s.
Run 2 (the 13 re-run after two test-side fixes): `logs/s7-run2.log` - **13 passed**, 242.39 s. Together every one of the 23 cells passed against the same installed wheel; no product code changed between the runs.

The two causes of the red run, both in the test code, not in the product:
1. `inspect_strict.group_offsets` called `committed_offsets` with its default `prefix_name='e09'` ("scratch offset observation identity differs") - hit 11 cells that read consumer-group offsets (retry-consumer kill, arrival DLQ, retry limits, O4-O8, bulk ordering). Fixed to pass `stack.prefix`.
2. The node-scale cell published relationships together with nodes in a schema without a DLQ; the edge loader found no endpoint and the run **failed closed with exit 1** (`did not resolve exactly one source and target endpoint`) - the correct behaviour. Fixed: wait for the nodes, then publish the edges (the same fix as the lease-kill cell in S4).

## Negative controls

- `stop --recover` against a live CLI is refused (cell above and unit test).
- The frozen-child cell exercises the SIGKILL escalation of `--recover` on a process that cannot act on SIGTERM; the unit test `ignore-term` does the same with a process that ignores it.
- The red run is the negative control for the helper fix: before the `prefix_name` change the same cells could not read offsets at all.
- The node-scale red case is evidence that an edge write without resolvable endpoints fails the run closed (exit 1) in process mode as in Docker mode.

## Docker-mode parity

- `--recover` semantics and the process/Docker difference after `kill -9` (above); the attempt directory is kept and must be removed by the operator.
