### Reds (kept, labelled)
1. **`file-healthy` (RED, product-rule quality, not fixed):** with a Feeder producing on every topic, `GraphLoaderConsumerLagNotDraining` was **pending** (not firing; `for: 15m`) in the 200 s window and again in `static-only`. Cause: the rule is `deriv(graph_loader_consumer_lag_records[10m]) > 0`; the CLI's lag for `EMPLOYED_BY` is 0-2 records and its 10-minute slope was **0.004 records/s** — any positive slope, however small, enters pending, and a healthy long-running stream with a producer will eventually satisfy `for: 15m`. The pass criterion ("a healthy run fires nothing", pending counts) is unchanged and the run stays red. **Orchestrator decision (recorded): the red stays recorded; the slope threshold becomes a `--values` parameter, default exactly today's `> 0`.** `GraphLoaderConsumerLagNotDraining` is now overridable (`alerts: {GraphLoaderConsumerLagNotDraining: {threshold: <records/s>}}`, `Param(kind="slope")` in `monitoring/export.py`); with no override the exported rule text equals the shipped file byte for byte (test), the rule file and every existing promtool outcome are unchanged (no promtool test of this alert existed). Added: generated boundary cases (`slope above T/s fires after 15m`, `a flat lag does not fire`, and for a non-zero threshold `slope below T/s does not fire`), a test of the override text and comment, and a control (a drifted recorded default makes the override fail loudly instead of doing nothing). **Not yet run through promtool**: the Prometheus image was removed at cleanup and none is available locally; running the new generated cases (and a mutated control) needs the image again (approval requested in the report).
