## Manual Twine environment and token handling (D07; also `docs/RELEASE_RUNBOOK.md` section 1)

- Environment: a throwaway virtualenv on the release operator's machine with only `build`, `twine` (versions pinned in `requirements-build.txt`: `build>=1.2,<2`, `twine>=6,<7`) and nothing from the checkout; artifacts are taken from a `git archive` build directory outside the checkout, never from the working tree or an old `dist/`.
- Credentials: one project-scoped API token per index (a first upload needs an account-scoped token for TestPyPI and for PyPI, which should be replaced by a project-scoped token after the project exists), kept in the operator's password manager. They are given to `twine` for the single command through the environment variables `TWINE_USERNAME=__token__` and `TWINE_PASSWORD`, or through a mode-0600 `.pypirc` outside the repository; never on the command line, in shell history, in the repository, logs or evidence. Registry pushes use `docker login ghcr.io --password-stdin` with a personal access token whose scope is limited to package writes. No workflow, no Trusted Publishing, no CI secret is added.
- The implementer (me) performs no upload; the release operator does each command after a specific instruction.
