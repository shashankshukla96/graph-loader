# E14.F3.S9 - host systemd user service

Real `systemd 255` **user** manager on the Linux host (`systemctl --user`, `systemd-run`-free: the shipped unit file is linked and started), no sudo, no lingering change, no Docker image; the product ran with `DOCKER_HOST` at a missing socket. The owned `e14` Neo4j/Kafka test containers are the only containers (user-approved throwaway infrastructure). No supervisor of our own stands in for systemd.

## Files

- `examples/systemd/graph-loader.service` (the unit), `graph-loader.env.example` (mode-600 `EnvironmentFile`), `README.md` (install, stop/restart table, KillMode rationale). Settings: `Type=exec`, `KillMode=mixed`, `KillSignal=SIGTERM`, `TimeoutStopSec=120`, `Restart=on-failure`, `RestartSec=10`, `StartLimitBurst=5`/600 s, `--health-addr 127.0.0.1:8081`, `--run-dir %h/graph-loader/runs`.
- Test: `tests/installed_service/test_service_systemd.py` (3 live cells). The test reads the shipped file and substitutes **only** the `%h/...` paths, the health port and (for the control) the `KillMode` line, links it as `e14-<owner8>-<cell>.service` (`systemctl --user link` + `daemon-reload`), starts it with `systemctl --user start`, and on exit stops it, `reset-failed`, removes its own symlink and reloads.

## Red runs kept

- Run 1 (`logs/s9-run1.log`, 2 failed): the helper read `cgroup.procs` of the *root* cgroup when the unit had none (`ControlGroup=` is empty after stop), so "nothing left in the cgroup" failed; fixed in the helper (empty group = no processes). Everything before that assertion had passed.
- The first draft of the unit comment claimed that the control-group stop makes the command exit non-zero; the host showed it exits 0 (the loaders exit 0 on SIGTERM too), so the comment and the README now state only what was observed: the order is not honoured.
