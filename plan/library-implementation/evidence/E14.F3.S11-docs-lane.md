## Source-vs-evidence/epic disagreements (the source is documented)

1. `/readyz`: the epic says "every required role running"; the source (`ProcessService.health_state`) is: at least one role running, none still pending, none failed, not stopping; a role that exited 0 is neither ready nor failed, so a finished bulk run reports not-ready. Documented as the source has it.
2. Stop timing figures: the systemd README says "about 50 s" from kill to `/readyz`, S9 evidence says 47-48 s. The page says "about 48 s".
3. S7 evidence quotes `retained: nothing beyond the attempt directory`; the source message is `nothing beyond the registry and logs`. Not quoted in the docs.
4. S4 evidence note 1 says metrics are disabled in children "until S5"; superseded by S5 (per-role loopback ports). Documented per S5/source.
5. Reserve vs measured: `cgroup_budget.ROLE_PEAK_MB` (node 150, writer 150, dispatcher 120, ...) are rounded-up peaks; the S6 measured VmHWM (node 97, writer 98, dispatcher 26, CLI 170, planner worker 144) is lower. The page shows both columns and states which is which. Lease server / clock / edge loader / retry consumer have no separate measurement; the page says so.

## Findings made while documenting (not fixed: `src/` is out of scope)

1. **Stream schema with no relationship types in process mode.** `_handle_start` returns 0 right after launching node loaders (`cli.py:2859`) and the `finally` cleanups run `ProcessService.close()`, which kills non-exited children. Docker mode deliberately leaves those containers running ("nothing supervises them"). Read from source, not run; documented as "not useful in process mode".
2. **`stop --recover` with `--runtime docker`** is accepted and silently ignored (it falls through to a plain node-loader stop). Documented as "no effect"; arguably should be refused like the other cross-runtime flags.
3. **`--replace-stale-plan-topic` in process mode.** The "no container of that run is alive" check (`planned_edges.replace_stale_chunk_topic` -> `ProcessService.list_run_containers`) only sees the current command's handles, so it is vacuous; its error text (`planned_edges.py:75`) also suggests `docker rm -f ...`. The docs tell the operator to run `stop --recover` first and read `remaining=[]`.
4. **`--metrics-addr 0.0.0.0` and `targets.json`.** The file then lists `127.0.0.1:<port>` (the runtime substitutes loopback for `0.0.0.0`), which only works for a Prometheus in the same network namespace. Documented.
5. `GRAPH_LOADER_METRICS_LISTEN` is read by `start_metrics_server` whenever no explicit port is passed, which includes the CLI's own server; the docs call it a runtime-set variable, not an operator setting, and I did not exercise it on the CLI's own endpoint.
6. The chunk-topic name appears in the CLI log as `stage=edge-plan-start plan_id=... topic=...`; there is no registry record of the run id before the dispatcher starts, so after a `kill -9` during planner scanning the docs point to the log line or a topic listing.
