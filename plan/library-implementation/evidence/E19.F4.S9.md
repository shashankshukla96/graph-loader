**Deviations from the text of D19-8 (all additive; none touches the shared daemon, firewall, DNS or the user's services):**
1. The registry also serves TLS with the throwaway CA. `docker buildx imagetools inspect` (used by `graph-loader images build` to resolve the base image) runs in the client and contacts the registry itself; the runner trusts the CA, the inner daemon keeps `--insecure-registry`. A plain-HTTP registry was **not** tried (see findings).
2. An owned DNS container and `--dns` on the inner daemon. BuildKit `RUN` steps do not see Docker's embedded resolver (127.0.0.11), so without an owned resolver `pypi` and `debian` could not be resolved inside a build (this is the real-world requirement of a restricted network too: its DNS).
3. The runner image is made with `docker create`/`cp`/`start`/`commit` in owned containers, not `docker build`: a BuildKit build on the shared daemon leaves cache records that this harness may not prune (see "Leftover").
4. The registry content (base image, Neo4j, Kafka) is pushed by the **inner** daemon: the shared daemon exports each image (`docker save`), the inner daemon loads, tags, logs in and pushes it, because only the inner daemon has the insecure-registry argument. The shared daemon never pushes.
5. The named `docker`-driver builder is the implicit `default` builder of a fresh `DOCKER_CONFIG` (S5 amendment); `docker buildx ls` in the runner shows `default*  docker  running  BuildKit v0.34.0  linux/amd64`.

## Findings for the docs (S11 / `docs/RESTRICTED_NETWORKS.md`)

1. **Name resolution inside builds.** BuildKit `RUN` containers use the daemon's `--dns`/host resolver, not the embedded DNS of the daemon's own container network; a mirror host name that works for `docker pull` may not resolve in a build step. The guide must say that the build host's DNS (or the daemon's `dns` setting) must resolve the index and Debian mirror names.
2. **A partial Debian mirror needs the archive layout including `by-hash`.** The Dockerfile's `Signed-By` keeps the Debian archive keys, so the mirror must serve the real signed `InRelease` and the index files by hash (`Acquire-By-Hash: yes`), not an unsigned flat repository. The harness's mirror (indices + `tini` only) is accepted by `apt-get update && apt-get install tini`.
3. **Registry transport.** `graph-loader images build` resolves the base image with the client's `buildx imagetools`; the client must trust the registry's TLS. The harness used TLS; a plain-HTTP registry reached only through the daemon's `--insecure-registry` was not tried and is not claimed to work.
4. **Containerd image store ids.** On Docker 29 with the containerd store an image id is its manifest digest and `RepoTags` lists `name@sha256:…` for a digest pull; the cleanup excludes that own reference when it decides whether other tags exist.
