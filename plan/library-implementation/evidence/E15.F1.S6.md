## Decisions (contract)

* **Stale threshold: 30 s** (`--stale-after SECONDS`, env `GRAPH_LOADER_STATUS_STALE_AFTER_S`). The CLI refreshes `heartbeat_at` from its own telemetry thread every status interval (5 s), independent of what the load is doing (planning, schema, waiting), so 30 s is six missed beats. A run whose state is `starting`, `running` or `stopping` and whose heartbeat is older is **stale**; a finished run (`succeeded`, `failed`, `stopped`) is never stale however old. With the SQL store a database outage also makes a run look stale (heartbeats cannot arrive), which is the honest reading: the reader cannot know.
* **Dead**: only when stale AND the controlling CLI is proven gone on this host: E14's registry `cli` record (pid + start time + boot id) no longer matches any process (gone, or the pid belongs to a different process: a recycled pid is proven by the identity mismatch), or, without a registry (Docker runtime, SQL listing), the document's own `host` is this host and its `pid` does not exist (a live pid proves nothing, so it never makes a run "dead", and a host that cannot be checked yields "stale", never "dead"). Dead and stale both exit 2; the label and the `reader.dead` flag tell them apart.
* **Exit codes**: 0 running (fresh) or succeeded, 1 failed, 2 stale / dead / unknown (nothing found, unreadable, schema-invalid), 3 stopped (130 on Ctrl-C).
* **`status` is the container listing unless run status is asked for (orchestrator decision, accepted).** Plain `graph-loader status`, and `status --run-dir DIR` alone, are exactly the output of earlier versions in both runtimes: the Docker parity golden pins the plain command (a `containers.list`) and E14 documents `status --runtime process --run-dir DIR` as the registry listing of node loaders (PROCESS_RUNTIME section 7), also for a run that now has a locator. Run status is selected ONLY by `--run`, `--json`, `--watch`, `--list`, `--execution-id` or `--refresh-lag`. `--containers` adds the old listing to a run-status view. `--run-dir` is accepted by the Docker runtime only together with one of those options; otherwise the "applies to --runtime process only" error stays, locator or not. (An earlier build of this story switched to run status whenever a locator was present; that was removed.)
* `--json` prints exactly one line: the (schema-validated) status document plus a `reader` member `{stale, dead, heartbeat_age_seconds, stale_after_seconds, exit_code, label}` (and `lag_refreshed`, `lag_refresh_error` with `--refresh-lag`); the open published schema accepts the extra member. Nothing else goes to stdout.
* `--list [--active] [--json] [--status-store json|sql]`: JSON store: every attempt under `--run-dir` (default the OS temporary directory) whose locator names the JSON store; SQL store: the executions of the database named by `GRAPH_LOADER_STATUS_DB_URL`. Newest first, each with its reader label; `--active` = not finished (stale and dead ones included, so they can be found).
* `--watch [--interval S]`: redraws only when something changed, ends when the run finishes or goes stale, with that exit code.
* `--refresh-lag [--refresh-timeout S, default 5]`: ONE query for each node label and relationship type (high watermarks and the group's committed offsets; group names exactly as the loaders derive them: `<prefix>-<label>`, stable stream groups, or the bulk phase's run-scoped group), the whole of it bounded by the deadline; the topics and groups come from the attempt's own `runtime_schema.yaml`. Nothing is written anywhere; a failure is a note on the output (`lag not refreshed: ...`, `reader.lag_refresh_error`), never an error exit; the stored values are shown untouched.

## Not covered

* The `status` view of a run whose store is SQL and whose locator is on another machine is limited to `--execution-id` + the database (no registry, no attempt directory): staleness yes, "dead" only for the same host.
* No colour, paging or terminal control in `--watch` (a plain redraw).
