## Design note D14-5 - node-only stream in process mode: supervise, not detach

**Finding (from reading the source in the docs lane, orchestrator request).** A stream schema that declares no relationship types takes the early return `if not edge_configs: return 0` in `_handle_start`. Docker mode documents and keeps that: the node containers are launched and left running unsupervised after the command returns. Process mode cannot: the roles are children of the command, tied to it by the control-socket lifeline, and `ProcessService.close()` runs on exit - so `start` returned 0 and the node loaders were gone; the user's schema loaded nothing, silently.

**Decision (orchestrator, option A).** In process mode the command stays alive as the node loaders' supervisor: `cli._supervise_node_loaders_only` runs the existing `_NodeLoaderWatcher` and the `/healthz` heartbeat until the shared shutdown event is set. A stop request (SIGTERM, SIGINT, `stop`) ends the loaders in order and the command exits 0; a node loader that dies makes the watcher set the event, the rest are stopped and the command exits 1 (same supervision contract as every other stream shape; fits `Restart=on-failure`). Docker mode is byte-for-byte unchanged (`test_cli_shutdown.test_stream_without_edges_leaves_its_detached_node_loaders_running` and the parity golden are untouched and green). Option B (refuse at start in process mode) was considered and not chosen.

**Tests.** `tests/test_node_only_supervision.py` (3), real `ProcessRuntime` children and the real `_supervise_node_loaders_only` in a stand-in command (`tests/fixtures/e14_node_only_standin.py`): the command stays up and a SIGTERM stops the loaders in order with exit 0 (they log `term`, none is killed); a SIGKILLed loader stops the rest and the command exits 1 with the supervision line; `kill -9` of the command ends the loaders through the lifeline. Live cell: after the service soak (to be added to this file).

**Docs.** `docs/PROCESS_RUNTIME.md` (section 3, and the limit removed from section 10) and `docs/INCREMENTAL_LOAD.md` (the B7 "not covered" sentence) state the difference: Docker returns and leaves the containers running, process mode supervises in the foreground.

## `test_logs_forms_and_size_cap` was flaky - cause and fix (product, small)

Reproduced on the Mac under CPU load: 6 failures in 40 runs (six `yes` hogs), always `assert ... st_size <= 2000 + 64` with 2305-2946 bytes. Cause: `_LogPump` rotated *before* writing a read chunk but wrote the whole chunk (up to 64 KiB) into the new file, so one large read (timing dependent) put the live log above the cap; the same boundary could also leave fewer lines in the live file than `logs(tail=N)` asked for. Fix: the pump slices a chunk to the room left (the file never exceeds the cap) and `ProcessHandle.logs()` returns the kept predecessor followed by the live file (continuous, like `docker logs`). After the fix 0 failures in 40 under the same load, plus a deterministic regression test (`test_a_single_burst_larger_than_the_log_cap_never_exceeds_the_cap`); the process/handle/observability suites are green (92 passed).
