## Boundaries for U3 (documentation and release notes)

Executed here, with the exact outcomes, unless marked otherwise:

- **`order_by` newest wins** across topics, partitions and replicas whatever the arrival order and offsets (O4/O5/O6, 3/3). A **tie keeps the stored value** (second record with the same version, different note: the first note stays), a **strictly older value is ignored**, and a **record without the `order_by` property is applied unconditionally** (it overwrote the note and left the stored version). Uncomparable value types being skipped silently is documented in B5 and was not executed.
- **Without `order_by`, the record applied last wins even if older**: a single-topic type given version 400 then version 100 ends at 100 (`test_without_order_by_the_record_applied_last_wins_even_if_older`). With several topics and `topic_conflict: arrival`, the result for a pair present in both topics depends on arrival order: in the DLQ exploration of S4, when both topics were published at once before the fleet started, 582 of 783 shared pairs ended with the older topic's value in two of three runs (the product's own warning: "resolve in arrival order, which is nondeterministic"). The maintained dataset test (S4) is deterministic only because it sequences topic b, then topic a. **No exactly-once or restart-safe arrival promise is made or implied** (D02).
- **Manual replay** can overwrite a newer value with an older one unless the type has `order_by` (O7).
- **Restart / revoke / eviction** of the retry consumer lose its arrival memory (O1–O3, unit counterexamples); `order_by` types are unaffected (O1 live).
- **Topic recreation**: stop the fleet first (O8); with the fleet stopped the restart is clean because Kafka removes the deleted topic's offsets; under a running fleet it is unsupported.
- The foreign `order_by` assumptions recorded in D02 (field validation, equal-version, missing/null value, external writers, replay) were exercised only as listed; **timestamp-typed `order_by`** and an external writer were not (the existing integration module covers them as opt-in developer-stack tests); `order_by` in the bulk modes is covered by the addendum.

### D08 shared-engine weakening: foreign images added during a run

The engine is shared with an outside workload that pulls images (`postgres:16.15`, `testcontainers/ryuk:0.14.0`, `node:24.22.2-bookworm-slim`; none used by E09,
none touched). The postflight (`scripts/service_lane.py::tolerated_foreign_images`, called from `verify_installed.py::service_postflight`) therefore tolerates a
foreign difference **only** when every changed category is images and their tag rows, no image is removed, replaced or re-tagged, containers, networks and volumes are
identical, and an added image is neither named, by tag or by repository digest, in a candidate repository (`ghcr.io/shashankshukla96/graph-loader-*`) nor carries the E09 owner label. The snapshot reads the image list once (ids, tags and repository digests come from one response and must
agree, every added id must appear in all three) and an existing image must keep its tags and digests. Added image
IDs, tags and digests go into the receipt (`service.postflight.foreign_images_added`) and the runner's summary line; anything else still fails. Controls: 19 in `tests/test_service_lane.py` (round-2 review: digest-only candidate image, digest gained or lost, disagreeing image tables, a changing image list read once; round-3 review: duplicate image ids and duplicate tag or digest rows are rejected before they become dictionaries).
The final lane run saw no foreign change, so this path is proven by the controls and by the red run above (which this rule would have tolerated), not by a green run that used it.
