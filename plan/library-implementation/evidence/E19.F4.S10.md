## What is proved, and how a denial is defined

The same probe runs unchanged in every place; each check prints one `PROBE {json}` line (kept in `final-run/isolation-probes.jsonl`, 44 rows, all `ok`). For a public target it records the DNS answer, a TCP connect to each answer and an HTTP request, and classifies every failure:
`network` (unreachable, no route, refused, timeout), `dns`, `tls`, `reached` (a status came back, even 401: the host was reached), `other`. **A denial counts only when DNS answered and every transport attempt failed with `network`.** A DNS failure alone, an authentication error and a missing image are never a denial
(unit tests for each; `classify_text` for pull and apt/pip output: a transport failure wins over the sentence "failed to authorize", which is how a registry client reports that it could not reach the token endpoint).

**The owned resolver answers the public names with their real addresses** (recorded at seeding, as a corporate resolver would): `registry-1.docker.io`, `auth.docker.io`, `index.docker.io`, `ghcr.io`, `pypi.org`, `files.pythonhosted.org`, `deb.debian.org` and the rest; owned names through Docker's DNS; NXDOMAIN for everything else. The runner, the inner daemon and (through the daemon's `--dns`) builds and
role containers all use it. So each denial is a transport denial, not a missing DNS record: the resolver log shows 53 public-name answers, 21 owned, 10 NXDOMAIN (`final-run/extra-checks.txt` and the `owned resolver answered the public names` step).

## Docs findings (for S11 / `docs/RESTRICTED_NETWORKS.md`)

1. **Single-label names do not resolve in an inner user-defined network** when they are only known to the upstream resolver (the embedded DNS answers inner container names only, appends the search domain to other single-label names, and does not forward the bare label). Role containers, which only need Neo4j and Kafka, are unaffected; anything else must be reached by a fully qualified name.
2. **A blocked route looks different in different places**: `ENETUNREACH` for a direct connect, a long connect timeout for `apt`/`pip` inside a build step. Health checks and alerts in a restricted network should treat both as "denied".
3. `apt-get update` exits 0 when every source fails to fetch; a check for a reachable mirror must read the warnings, not the exit status.
4. `pip` prints no network message unless it retries at least once.
