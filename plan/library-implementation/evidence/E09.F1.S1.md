## Findings

- **Product:** none. Behaviour matches the dispatcher's documented contract. Observed details worth keeping: the surviving writer's in-flight chunk can still commit after the failure (so rows done can exceed the count at the instant of the kill); a failed attempt keeps `edge-plan.json` but writes no `*.ledger.json`; the replay creates a new plan and a new run-scoped chunk topic, so `--replace-stale-plan-topic` was not needed (the killed run's chunk topic did not remain in the broker's topic list).
- **Own harness defects fixed this story** (red runs kept under `var/e09-validation-20261028/s1/` and on the host):
  1. After a killed client Neo4j logs the terminated query at `ERROR` in the completion format plus failure text; the structured parser rejected it ("identity differs") and a killed writer can also leave a query that started and never ended. Fixed fail-closed: a well-formed ERROR failure is one terminal `failed` record; open queries are accepted only with `allow_open`, accounted for exactly, and a query open at the first mark may end later in the window. 14 new controls; the two old frozen "ERROR rejected" tests are unchanged and still pass.
  2. `explore-1..4`, `dry-1`: exploration/assembly and the open-query case above. `explore-2`: runner rejects a trimmed lane (expected).
  3. `final-1`, `final-3`: the bulk tests ran after the destructive log-continuity test, which moves `/logs/query.log`; the error text ("unavailable or exceeds its bound") made me raise the bound to 32 MiB in `final-1` — a misdiagnosis, reverted to 8 MiB (logs were ~0.4 MB). The lane order is now enforced by file name: `test_service_load_bulk.py` sorts between `test_service_harness.py` and `test_service_log_continuity_live.py`.
  4. `final-4`: all 97 tests passed but the runner failed the receipt because the frozen ID order differed from execution order; `final-5` was refused ("service IDs … reordered") for my wrong fix; renamed the file instead (`final-6`).

## Not covered or weakened

- No claim of distributed exactly-once writes: replay convergence relies on MERGE (idempotent relationship writes).
- The kill is a timing race against 80–250 ms chunks. The test requires that the writer really held a chunk and fails otherwise; it held one in 3/3 repeats of `final-6` and in every earlier kill run that reached that step (`explore-4`, `explore-5`, `dry-2` 3/3). The small 60/6/120 fixture is too fast for a mid-chunk kill (about 20 ms per chunk), so the kill and the lock-wait scale tests use the 3000/30/6000 fixture, and B1 uses the approved small one.
- Scale, hubs (the 6000-edge fixture has none), spill and multi-partition planner input are not exercised. Node-loader failure/restart, Neo4j outage mid-run (S5), DLQ (S4), arm64 (E11) are not covered.
- The lock-wait detector is proven on the injected non-rolling structured appender, not the shipped rolling appender; ID contiguity is an observed property of Neo4j 5.26.32. A query that fails before it is logged would not be visible.
- Native shared Docker Engine substrate: unlabelled CLI containers are adopted by candidate image + owned network + non-pre-existence, not by creation provenance; the CLI holds socket authority. No daemon fence.
- Only `final-6` is a passing run at these exact bytes. The lane's S7 IDs ran in it too, but the S7 lane must still be rerun at E09's final bytes.
- Did not run: the other installed lanes, the macOS regression lanes after the last edits beyond the local unit checks below, independent review.
