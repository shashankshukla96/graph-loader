**Conclusion: environment, not a product regression.**

Options for the user: (i) treat the 0.3 s bound as a documented limit of the guarded amd64-native-Engine container route (no product impact: the same test passes unguarded and natively); (ii) profile the guard's per-process cost in the container and fix it in `scripts/installed_guard*.py` (tooling only; refreeze not needed because scripts/ is not an inventory stage file, but a commit and a rerun of the amd64 cells would be); (iii) rerun the amd64 cells on a Docker Desktop VM again. ## amd64 service-harness: diagnosis, test-only fix and final result, 2026-11-02

The two red runs above are retained. Diagnosis (details in the manifest, `gates.e09_service_harness_amd64_rebuilt_images`):

- **(a) `test_s5_stream_stops_gracefully_with_work_outstanding_and_resumes[1]` is a test-workload race.** In run 1 the relationship writes lasted 1.55 s (68 write queries); the first SIGTERM event landed 1.46 s after the first write and 0.09 s before the last, about 94% through, so the graceful stop drained the rest (6000 of 6000). The test published all three relationship topics (about a second) before it started watching for work in flight, while the loaders were already writing; the idle host shortens the window further.
- **(b) `test_s5_stream_stops_when_an_edge_loader_is_lost_and_resumes[1]` is the same race, not a CLI defect.** The CLI waits `session.timeout.ms + 5 s` (about 50 s) for the killed loader's group member to expire; that is the designed safety wait. The first run had already written the whole graph before the kill, so the test's resume assertions held at once and it SIGTERMed the second CLI while it was still waiting, giving exit 1 "nothing was started".
- **(c) Run 1's 20 follow-on failures are a cascade.** The failed test never reached its trailing `clear()`, so 2,006 nodes and 6,000 relationships stayed in the shared scratch database. The next whole-database observation crossed its 2 MB byte bound and raised mid-iteration; the abandoned result left a started-but-never-completed query in Neo4j's query log. Neo4j never logs its end, so `declare_open_writes` rejected it (3 failures) and every later strict query-log capture waited 30 s for quiescence that could not arrive (15 timeouts). Independent tests after the root failure could not run their real assertions.

**Fix (test-only, `tests/installed_service/`; no `src/`, wheel or sdist change):** `producing()` publishes the relationships from a thread while the test watches for work in flight, so the stop or kill lands with records unpublished or unconsumed, and the loader-lost test also asserts that it left work outstanding; `graph_observations` consumes its result in a `finally` so an abandoned observation still completes in the query log; an autouse conftest fixture wipes the owned scratch graph after a failed test. The inventory was refrozen: three file hashes changed, 4,145 IDs, order and dispositions unchanged. Diff: `var/e11-validation-20261101/f2amd64/testfix.diff`.

**Final run (once, after the fix):** the full 150-ID service-harness lane on the rebuilt amd64 image IDs, wheel `b420c784…e199`, inventory `561ec664…`: **150 passed** in 1,541.6 s. Foreign snapshots before/after equal; no owned resource remains.

**Status:** every gate is pass or accepted by user decision (the two accepted-harness-limit items from E11.F1.S3 are unchanged). The test-only fix and the refrozen inventory are uncommitted. E11.F2 has not started.
