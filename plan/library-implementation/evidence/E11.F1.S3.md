`test_order_by_newest_version_wins_in_planned_lease_and_classic_bulk[classic]` fails at its final assertion `superseded > 0` in both runs. **Conclusion: environment, not a product regression.**
1. Product code is not the variable: the E08 wheel (b) fails exactly like the final wheel (a), and `git diff 410ae7f 60ea29f -- src` is only `_version.py` and the refusal text in `cli.py`; no planning module changed (`git log 410ae7f..60ea29f -- src` shows no commit touching `planning*`).
2. Not the Python patch release: 3.12.14 (c) is as red as 3.12.16.
3. The lever is the runner's per-process guard: the same test, wheel and container run at 0.07–0.10 s without it and 0.51–0.59 s with it, past the 0.3 s bound, and the bound is applied to a window that includes the synchronous spawn of the planner's workers (`start()` submission is, per `docs/LIBRARY_API.md`, outside coordinator cancellation). Natively on the same host (venv, system CPython 3.12.3, guard on) the ID passes in every lane run, so the extra cost is container specific. What changed since E08 on this host is the Docker runtime: E08 ran its amd64 cells in the Docker Desktop Linux VM (kernel 6.10.14-linuxkit, per `reviews/e08-s2-full-review-20261028.md`); the host now runs the native Docker Engine 29.9.0 on kernel 7.0.0-38 (E09 migration, 2026-10-30). I did not identify which part of the guard is slow there (it hashes and logs on each Python start) and did not profile it; that is the next step if the user wants this gate green rather than documented.
4. Ruled out in this and the earlier runs: network (offline fails), read-only root, seccomp (`unconfined` fails), host load (idle host), the E08-era Python patch release.

Status of the gate stays **red** on amd64 (`public-contracts` in the container route, both cells); arm64 containers pass. Options for the user: (i) treat the 0.3 s bound as a documented limit of the guarded amd64-native-Engine container route (no product impact: the same test passes unguarded and natively); (ii) profile the guard's per-process cost in the container and fix it in `scripts/installed_guard*.py` (tooling only; refreeze not needed because scripts/ is not an inventory stage file, but a commit and a rerun of the amd64 cells would be); (iii) rerun the amd64 cells on a Docker Desktop VM again. No product change is indicated by this investigation, so the candidate bytes stand.

Foreign snapshot (host) after the investigation: the only change versus the previous snapshot is the image `python:3.12.14-slim` that I pulled; no container, network or volume differs; no e11-owned resource remains. The Mac was not used.
