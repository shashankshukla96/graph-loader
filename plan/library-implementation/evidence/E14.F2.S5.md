## What was built

- **Per-role loopback metrics ports.** `utils/metrics.py`: new `GRAPH_LOADER_METRICS_LISTEN` (`host:port`, port 0 = OS-assigned), read only when the caller passed no explicit port - Docker mode never sets it, so it is unchanged.
  `metrics_status(server)` returns `{"state": "listening", "port"}` / `disabled` / `failed`. Every role's `runtime_ready(...)` now reports it (`_child_protocol` carries a `metrics` field). `ProcessService` sets `GRAPH_LOADER_METRICS_LISTEN=<--metrics-addr host>:<port or 0>` for each child; the operator's `GRAPH_LOADER_METRICS_ENABLED=0` still disables (the builders pass it through).
  This replaces S4's interim `GRAPH_LOADER_METRICS_ENABLED=0`. `--metrics-addr HOST[:PORT]` defaults to `127.0.0.1` (use `0.0.0.0` inside a pod, D14-4); a fixed port only suits a single role.
- **Prometheus `file_sd`.** `<run dir>/metrics/targets.json`, rewritten atomically (temp file, fsync, rename) on every role ready, exit and forget (replacement). One group per live role with a listening endpoint (`targets: ["127.0.0.1:<port>"]`, labels `exporter`, `runtime`, the role's Docker-equivalent labels with dots removed: `component`, `kind`, `run_id`, `node_label`, `edge_type`, `replica_id`...); a role whose endpoint is `disabled` or `failed` gets a group with **no targets** and `metrics_state`; exited roles disappear; the CLI's own endpoint is listed (`set_cli_metrics`).
- **Health.** `--health-addr HOST:PORT` (off unless given; port 0 allowed, the port is logged as `stage=health`): `GET /healthz` = the CLI answers and its registry is writable; `GET /readyz` = 200 only when at least one role runs, every launched role has reported ready, none has failed (exited non-zero without being asked) and the run is not stopping; the body names `pending`, `failed`, `stopping`, counts. A role that finished with exit 0 is neither ready nor failed. Anything else answers 404 JSON.
- **Child log relay.** `--child-logs {relay,files}` (default `relay`): each child's output is always written to `<run dir>/logs/<name>.log` (size-capped, one rotated predecessor); `relay` additionally forwards each complete line to the CLI's stdout as `[<name>] line` through a bounded queue and one writer thread. A stuck stdout makes the queue fill and further relay lines are *dropped and counted* (reported at close); the pump keeps draining the child's pipe, so a child never blocks on logging.
- CLI: `--metrics-addr`, `--health-addr`, `--child-logs` are start options for `--runtime process` only (refused in Docker mode: `... applies to --runtime process only`).

## Notes for E15 / docs

- Per-child `file_sd` targets are only reachable from the host (loopback); a Prometheus in another pod or host needs E15's aggregated endpoint. In a single container set `--metrics-addr 0.0.0.0` so the pod address reaches each role.
- `/healthz` proves the CLI answers and the registry is writable; it does not prove the supervision loop is making progress (no loop heartbeat exists today).
- Relative paths in a schema resolve against `<run dir>/work/<name>/`.

## Follow-up (orchestrator review): `/healthz` means "the supervision loop is alive"

- New `orchestrator/heartbeat.py`: a process-wide `beat()` / `age()`. The supervision loops tick it once per iteration: `RelationshipBulkMonitor.supervise_stream` and `_wait`, `BulkMonitor._wait_until`, and the planned phase's poll loop (`planned_edges.run_planned_edge_phase`).
- `ProcessService.alive()`: unhealthy when the registry writer is broken, or when the newest beat is older than `--health-stale-after SECONDS` (default **30 s**, `health_stale_after=` in the API). Before the first beat (start-up, schema apply, launching) there is nothing to judge and `/healthz` is 200.
  *Threshold:* the review asked for 3 x the loop interval. The nominal tick is 0.25 s, but a healthy tick can legitimately take several seconds (lag refresh and group-membership checks make admin round trips with 2 s timeouts, per edge type), so 3 x 0.25 s would flap. The default is 3 x 10 s, where 10 s is the longest healthy tick; it is configurable.
- Controls (all in `tests/test_process_observability.py`): no beat yet -> 200; beating -> 200; **stalled loop (no beat for longer than the threshold) -> 503 `unhealthy`**; beating resumes -> 200; a loop thread that keeps beating for longer than the threshold stays 200 and, once it dies, turns 503 within the threshold; the real `supervise_stream` and the monitors' `_wait` loop do tick the heartbeat (real monitor over `MagicMock` Kafka); `--health-stale-after` is refused in Docker mode.
- Docker mode: unchanged (the beat is a no-op timestamp write); golden parity and the monitor tests pass.
- Result: `tests/test_process_observability.py` 22 passed (18 + 4 heartbeat tests) on the Mac.
