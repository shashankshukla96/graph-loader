**Approach and why.** The Debian `tini` package of the base image, with the upstream version asserted at build time, rather than a downloaded GitHub release binary with a checksum:
- one signed apt transaction, identical for amd64 and arm64 (the S8 arm64 build needs no per-architecture binary or checksum table, and nothing is fetched outside the distribution mirrors);
- the checksums of the release binaries could not be verified in this lane (no network), and an unverified pinned checksum would fail the live build for a reason unrelated to the product;
- the pin is the *upstream* version (`ARG TINI_VERSION`, asserted against `tini --version`, so a base image that ships another tini fails the build loudly). The Debian *revision* is whatever the base image's release carries; byte reproducibility of the image is therefore bounded by the unpinned `python:3.12-slim` tag, exactly as it already was (the image bytes change anyway: D14-3). If the user wants a byte-pinned tini, the alternative is `ADD` of `tini-static-$TARGETARCH` with a `sha256sum -c` per architecture; the checksums must then be copied from the v0.19.0 release page by someone with network access.
- The `apt` layer comes first, so the existing dependency layers and their cache keys are untouched; `rm -rf /var/lib/apt/lists/*` keeps the layer small (tini itself is tiny).
- No `-g` (the plan: the CLI signals its own process groups and must run its ordered planner cleanup first), no `-s`: tini is PID 1, so it already reaps orphans. Docs note: in a pod with `shareProcessNamespace: true` tini is not PID 1 and warns; set `TINI_SUBREAPER=1` there.

**Image contract unchanged.** Labels (`org.opencontainers.image.version=$GRAPH_LOADER_VERSION`, `.source`, `io.graph-loader.component="cli"`, `io.graph-loader.image-contract="1"`), `ARG GRAPH_LOADER_VERSION`, the `m.version(...) == sys.argv[1]` check, `pip install --no-cache-dir --no-deps .`, `WORKDIR /app`, no `CMD`/`USER`: all unchanged (asserted by `tests/test_dockerfile_single_container.py`, and by the existing `tests/test_candidate_images.py`, which still passes). The entrypoint *list* changes by a `tini --` prefix; the argument semantics are unchanged (`docker run <cli image> start ...` still ends up as `python -m neo4j_graph_loader.cli start ...`).

**Docker mode is unaffected (checked).**
- Docker mode never creates a container from the CLI image: `cli.py` resolves only `node`, `edge` and `clock` (`prepare_images`), and the preflight/lease/planner/writer containers use those images with an explicit `entrypoint=[...]` override (`docker_service.py`, `_docker_preflight.py:65`, `tests/test_docker_service.py`). The frozen golden `tests/golden/docker_parity_0.1.0a1.json` names no CLI image and records only `["python","-m",<role module>]` entrypoints; `tests/test_docker_parity.py` passes.
- `Dockerfile.node_loader`, `.edge_loader`, `.clock` are untouched and contain no tini (Docker mode gives them Docker's own init: `docker_service.py` already waits for `docker-init`/`tini` in `top()`).
- Existing image checks stay green: `test_candidate_images.py`, `test_image_selection.py`, `test_docker_service.py`, `test_distribution_foundation.py`. `scripts/build_candidate_images.py` hashes `Dockerfile` into `input_sha256`, so a new candidate manifest is required (expected: D14-1 re-freeze). `tests/test_docker_build.py` is an integration test of `Dockerfile.node_loader` only.

## 4. Finding: the group-level OOM report does not exist yet; proposed patch (NOT applied)

`grep -rn "victim\|memory.events\|oom_kill" src` finds nothing outside the S6 *test* sampler: the plan's "cgroup OOM kill observed; victim unknown" failure text was never implemented. `ProcessHandle.attrs` returns `OOMKilled: None` and no call site reads it, so an OOM-killed role is indistinguishable in the CLI output from a manual `kill -9` (exit 137). The two OOM live cells (and the control) assert the message and will fail until it exists. Proposed minimal patch (new `OomWatch` in `cgroup_budget.py`, one hook in `ProcessHandle._reap`, one method and one constructor argument on `ProcessRuntime`; plus a new unit test file). Design: the CLI's leaf cgroup `memory.events` `oom_kill` counter is baselined at runtime construction; whenever a child exits by SIGKILL the counter is re-read, and a rise is reported once, to stderr and as an `oom` registry record, without naming any child; no rise (manual kill) -> silent; rise with two SIGKILLs -> one report. It is applied after the `exit` receipt and before the handle's exit event, so the report precedes the CLI's own failure message. Verified in a scratch copy (see section 3). ## 5. Notes for the later single-container docs

- Run: `docker run --rm --user $(id -u):$(id -g) -e HOME=/tmp -v $PWD/run:/work -w /work --env-file ... -p 8081:8081 <cli image> start --mode stream --config /work/schema.yaml --runtime process --run-dir /work/runs --health-addr 0.0.0.0:8081 [--metrics-addr 0.0.0.0]`; no `/var/run/docker.sock`, no `--privileged`, no network creation. Probes: `/healthz` liveness, `/readyz` readiness. (The live cells use `GRAPH_LOADER_METRICS_ENABLED=0`; the metrics-on container shape with `--metrics-addr 0.0.0.0` is not exercised by them.)
- Stop budget: `docker stop` defaults to 10 s, shorter than the ordered stop of a loaded fleet. Document `docker stop -t`/`--stop-timeout`, compose `stop_grace_period`, k8s `terminationGracePeriodSeconds` = the CLI's stop budget plus margin (S9 uses 120 s for the unit).
- Restart: `--restart on-failure[:N]` (a role loss exits 1; an ordered stop exits 0 and is not restarted). `unless-stopped`/`always` would also restart after a clean exit 0 of a bulk job: use `on-failure` for streams and no policy (or a Job) for bulk. After an abrupt end the restart needs the group-member wait before ready (E13 finding B); allow `/readyz` several minutes (the cells allow 300 s).
- Memory: `--memory` + `--memory-swap` equal; the cgroup sizing (S6) reads the container's limit; an OOM kill ends the run with the group-level message (once the patch lands), never a named victim.
- Keep the run directory on a volume if the registry/logs should survive a container restart; otherwise the default OS temp dir inside the container is lost with it.
- `docker exec <c> python -m neo4j_graph_loader.cli stop --runtime process --run-dir /work/runs` is the second-shell stop (not covered by a live cell here).
- arm64: build with `docker buildx build --platform linux/arm64 --load` and record emulated vs native.
