## Behaviour

* **Labels on every sample.** `run_id`, `execution_id`, `exporter`, `runtime` are added to every sample of the process's registry at exposition time (HTTP endpoint and `metrics-*.prom` snapshots), by a collector over the unchanged registry, so no metric definition, call site or existing label changes. A sample's own labels win (`graph_loader_exporter_up{exporter}` keeps its own). Outside a tracked run (no `GRAPH_LOADER_EXECUTION_ID`) nothing is added: an untracked process or a library user sees today's output.
* **Source of the values: the three S2 keys only.** `execution_id` and the incarnation come from `GRAPH_LOADER_EXECUTION_ID` and `GRAPH_LOADER_INCARNATION` (the keys S2 already injects in Docker and the process runtime); `run_id` from `GRAPH_LOADER_RUN_ID` where the launcher already set it (node and edge replicas, planned writers, retry consumer); `runtime` comes from an explicit `GRAPH_LOADER_RUNTIME=process` that ONLY the process runtime sets for its children (orchestrator follow-up: never inferred from `GRAPH_LOADER_METRICS_LISTEN`); absent means `docker`. `test_runtime_is_explicit_never_inferred_from_the_metrics_listen_key` (Docker-style env with METRICS_LISTEN set and no RUNTIME key labels `docker`); controls C11 (children get no key) and C12 (inference restored) are red. **No Docker change**: the Docker parity trace and `tests/golden/docker_parity_0.1.0a2.json` are untouched (parity suite: 55 passed).
* **`exporter`** = `<kind>-<name>-r<replica>-<incarnation[:8]>` (`lease-server-1a2b3c4d`, `node-Person-r0-…`, `planned-writer-KNOWS-r3-…`; the CLI is `cli-<execution[:8]>`). Unique per incarnation: a restarted role is a different exporter, so the old series go stale and the new ones do not collide. The file_sd group of the same role carries the SAME `exporter` (computed by the CLI from the launch labels and the incarnation it also gave the child), so `up{exporter=...}` and the sample labels name one thing. E14's file_sd `exporter` (the handle name) moved to the new `role` label.
* **`run_id` may be empty.** A stream started without `--run-id` has none: the label is `""`, which Prometheus treats as absent; `execution_id` is the key that always exists. In the process runtime every role gets `GRAPH_LOADER_RUN_ID` (a process-only environment addition, derived from the launch labels). **Docker limit (carried to S9/S13):** the roles the Docker launcher never gave `GRAPH_LOADER_RUN_ID` (bucket lease server, planned dispatcher, clock) export `run_id=""`, because adding the key would change the Docker environment, which this story must not do. Dashboards and rules therefore select by `execution_id` and `exporter`, and treat `run_id` as optional.
* **Reserved names.** The four are reserved; `identity.validate_extra_labels` raises `ReservedLabelError` for any of them (wired into `--extra-labels` in S10).
* **Docker discovery.** Docker SD cannot derive the incarnation-qualified `exporter` (the containers have no label for it and none may be added): S9's Docker-path health uses `up` by container name. Samples carry the exporter anyway, with `honor_labels: true`, so the scraped value is kept.

## The aggregated endpoint (D15-3)

`graph-loader start --runtime process --metrics-port N` (process runtime only: `--runtime docker` refuses it with the same error as the other process-only options; `--metrics-addr`'s host is the bind address, default 127.0.0.1; `0` means OS-assigned) serves ONE `/metrics`:

* The CLI's own registry (with its identity labels) plus a parallel scrape (thread pool, 2 s timeout per child) of each live child, whose address comes from `ProcessRuntime.build_targets()`; the CLI's own group is skipped (its registry is merged directly).
* One `# HELP`/`# TYPE` per family; a sample whose label set is already present is dropped, and so is a family whose type disagrees with the first one seen; both are counted and logged once per scrape as a warning.
* `graph_loader_exporter_up{exporter,run_id,execution_id,runtime}`: 1 when the scrape of that child worked, 0 when it failed (its series are then absent from this scrape), 0 for a child whose endpoint failed to bind (`metrics_state=failed`); a child with metrics disabled by choice has no row.
* An exited child is no longer in `build_targets()`, so it disappears at the next scrape; a restarted role is a new exporter.
* A deployment scrapes the children (file_sd) OR the aggregate, never both; the same exporter from two jobs would double-count (S9 ships an alert for it).

## Cardinality budget (restated)

Constant labels add no series within one exporter: `test_identity_adds_no_series_within_an_exporter` compares the series of one exporter with and without identity (same count, same label names apart from the four). What grows is the number of exporters over the retention window: `test_series_churn_is_linear_in_exporter_starts_and_per_exporter_constant` runs six executions that REUSE one `run_id` and shows series per live exporter constant, no series shared between executions, and the union exactly `executions x series-per-exporter`. Budget: new series per execution = series of one exporter x exporters started (retries and restarts add one exporter each); `run_id` multiplies nothing. The catalogue is 32 families; `exporter_up` adds one series per exporter.

## E14 behaviour change (flagged; accepted by the orchestrator as a contract change to E14's unreleased file_sd format)

The process runtime's file_sd `exporter` label changed value (handle name -> unique per incarnation; the old value is now `role`) and the CLI group became `cli-<execution[:8]>` with `run_id`/`execution_id`.
