## Design as built

- `Handle` (protocol): `name`, `id`, `labels`, `status`, `attrs`, `reload()`, `logs(...)`, `stop(timeout=…)`, `remove(force=…)`, `top()`; every method raises `HandleGone`
  when the role is gone. `attrs["State"]["OOMKilled"]` is documented as `bool | None` (`None` = unknown); no call site reads it today.
- `Runtime` (protocol): the `DockerService` operations (`preflight_topology`, `prepare_images`, `build_image/edge/clock`, `run_global_batch_clock`,
  `run_bucket_lease_server`, `bucket_lease_address`, `run_planned_dispatcher`, `planned_dispatcher_addresses`, `run_planned_edge_writers`, `run_edge_loader`,
  `run_retry_consumer`, `run_node_loader`, `stop_node_loaders`, `list_run_containers`, `list_node_loaders`). `DockerService` satisfies it unchanged.
- `DockerHandle` delegates every call unchanged (same positional/keyword arguments reach the SDK) and maps only `docker.errors.NotFound` to
  `HandleGone` (`__cause__` kept); every other exception propagates as raised.
- `cli._sweep_orphaned_lease_containers` no longer reaches into `docker_service.client`; it calls `list_run_containers(label_filters=(…))`, which issues the
  identical `containers.list(all=True, filters={"label": […]})`.
- `--runtime {docker,process}` (`dest=runtime_backend`, default `docker`, env `GRAPH_LOADER_RUNTIME`) on `start`, `stop`, `status`, `replay-dlq`.
  `args.runtime` still holds `RunPaths`. `process` fails before any work with `stage=runtime reason=the process runtime is not implemented yet; use --runtime docker`
  (exit 1) for `start/stop/status`; `replay-dlq` never touches a runtime, so it accepts the option and behaves identically. An unknown env value is refused.
- Retained on purpose (to be taken over by S2/S4): `cli.py` still imports `DockerService` (the Docker backend constructor, called only from `_build_runtime`) and
  `wait_until_stop_signal_ready` (generic over `Handle.top()/id`, lives in `docker_service.py`). Neither imports `docker` itself.

## Findings and open points for the orchestrator

1. **`test-inventory.json` is an exact-match gate.** `scripts/freeze_installed_inventory.py check` requires the collected IDs to equal the frozen list in order, the
   test-file set to equal `file_dispositions`, and the sha256 of every `stage_files` entry to match. S1 adds two test files (`test_docker_parity.py`,
   `test_runtime_boundary.py`, plus the golden and `docker_parity_support.py` helper) and edits the bodies of six staged files (`test_stop_signal_ready.py` in addition to `test_cli.py`,
   `test_cli_shutdown.py`, `test_docker_service.py` in lane `cli-runtime`; `test_cli_shutdown.py` in `writer-runtime`; `test_bulk_monitor.py`,
   `test_relationship_bulk_monitor.py` in `orchestration-runtime`). I did not edit `test-inventory.json`: refreshing it needs `--freeze` with a wheel and sdist,
   which rewrites the artifact contract. Existing collected IDs are unchanged (no test added to, renamed in or removed from those files). Recommendation: do the
   inventory refresh once, at S11 (additions + the six re-hashed files), as the plan already schedules; decide if you want it earlier.
2. **The overlap flag is ignored in planned mode.** `--bulk-edge-overlap` is classic-only (a warning otherwise); the planned scenarios therefore trace identically
   for default/labels/shared, and the two overlap variants that change behaviour are the `--edge-classic` scenarios. Both are covered.
3. **`--stream-clock-rotation`** was first left out (the default schema fails the `mixed-stream` clock isolation policy); added in the follow-up below.
4. **Scripted monitors for end-to-end flows.** Kafka-side waiting (`wait_for_completion`, drain, lag) is replaced by doubles in the CLI-level scenarios, so the
   trace proves the Docker behaviour of the CLI/`DockerService`/`planned_edges`, and the monitor↔handle behaviour is proven by the two real-monitor scenarios, not
   by a full Kafka simulation.
5. `cli.py` still depends on the Docker module for `DockerService` (one constructor call in `_build_runtime`) and `wait_until_stop_signal_ready`; S2 should move the
   latter behind the handle protocol (a process handle's `top()` has no `docker top` equivalent) and S4 replaces `_build_runtime`'s `docker`-only branch.
