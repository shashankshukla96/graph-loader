## What was built

- `loader/edge_planner.py`
  - `PlannerSupervision(parent_watch, on_process)` (frozen dataclass, default **off**), accepted by `ParallelEdgePlanner` and `KafkaEdgePlanner` (`supervision=None`).
  - With `parent_watch`, each spawned worker gets a second socketpair ("parent-death socket"). The worker closes the duplicate of the parent's end it received (otherwise it would never see EOF),
    then runs `_watch_parent` in a daemon thread **independent of its command loop**: end of file means the CLI is gone (including `kill -9`), and the thread `os._exit(143)`s the worker at once,
    interrupting a scan that is blocked in Kafka. The parent releases its end only **after** `_cleanup_process_workers` has joined/killed the workers, so an ordinary ordered cleanup (stop frame, join, terminate) never trips it.
  - `on_process({"role", "index", "pid"})` is called in the parent for every worker (`planner-worker`) and for the multiprocessing resource-tracker helper (`planner-helper`, the "helper process").
- `orchestrator/planned_edges.py`: `start_kafka_edge_planner(..., supervision=None)` passes `supervision` to the planner factory **only when given**, so Docker mode calls the factory exactly as before.
- `orchestrator/process_runtime.py`
  - `ProcessRuntime.register_external(role, pid, index)` writes a `started` record (with start time and boot id) for processes the runtime did not spawn, so registry recovery can find them after a CLI death.
  - `add_pre_signal_hook` / `run_pre_signal_hooks`: hooks run **once, before the first group signal** (`remove(force=True)`'s `killpg`) and at the start of `close()`; a failing hook is reported and does not block signalling.
    The CLI registers its planner cleanup here when S4 wires `--runtime process`, which implements "the CLI stops planners before signalling any process group".
- Docker mode: **no behaviour change.** Supervision is opt-in; with `None` the worker is created with its original 8 arguments and no extra socket (asserted); the golden parity trace is still equal.

## Findings

1. A defect of my own, caught by existing tests: `_ProcessWorker.start`/`release_lifeline` read `_death_child` directly, and `tests/test_public_cleanup.py` builds fake workers that subclass `_ProcessWorker` without running `__init__`
   (15 failures on the first full run). Fixed with `getattr` defaults; these tests are the Docker-mode planner contract and now pass unchanged (96 planner tests green together).
2. The planner's Kafka scan loop (`scan_kafka_tasks`) has no cooperative cancel hook (only `SourceTask` scans take `check`), so a prompt `os._exit` is the interruption mechanism. Consequence: spill files stay in the run's spill directory exactly as they do after any failed run (evidence is retained; `replace_stale_chunk_topic` already handles the chunk topic on a rerun).
3. **Leftovers after a CLI death.** `os._exit(143)` in a worker skips its own cleanup: the planner's spill directory (`.edge-plan-spill-*`), the plan lock, `<plan>.progress` and any failure marker stay in the run directory under the existing "retained ownership, failure markers inspectable" contract. Nothing deletes them automatically; S4 or the docs must say who does (proposal: the registry recovery in S7 reports them and the operator removes the retained attempt directory, exactly as after a Docker-mode planner failure; the next run uses a fresh attempt directory and `replace_stale_chunk_topic` handles the chunk topic).
4. Under `-I`/spawn the workers inherit the CLI's stdout/stderr; the watch writes its warning with `os.write` and ignores `OSError`, so a broken pipe cannot stop it (the S2 lifeline lesson).
