## Findings

* **confluent-kafka / librdkafka SIGSEGV (dependency).** `AdminClient.list_consumer_group_offsets()` crashed the harness process (`rd_kafka_cgrp_op` <-
  `rd_kafka_handle_OffsetFetch` <- `ListConsumerGroupOffsetsResponse_parse`, backtrace in `var/e13-s1/sigsegv-backtrace.txt`) when the group coordinator was
  loading or moving. Minimal independent reproduction `var/e13-s1/repro_admin_offsets.py` (no graph-loader code): 2 broker-restart cycles, child exit -11, on
  **every** confluent-kafka tried: 2.5.3, 2.8.2, 2.11.1, 2.13.2, 2.16.1, i.e. the whole range the wheel allows (`>=2.5,<3`). The product calls the same API at stream
  start (`stream_groups.committed_offsets`) and in the bulk monitors. Probe `var/e13-s1/repro_cli_start_after_broker_restart.py`: the installed CLI started the
  moment the broker answered after a restart, 5 of 5 cycles, never crashed (it reaches its Kafka group calls about 5 s after it starts). Not a product failure here;
  an exposure to note for the release decision (a CLI SIGSEGV leaves its containers running, the recovery recipe below). S2's Kafka-restart fault observes the running CLI.
  The soak reads committed offsets with an unsubscribed consumer instead (`Kafka.committed`, as E09 does).
* **Restart after a loader loss waits for the dead member.** With `--stream-group-member-wait-seconds 20` the restarted CLI exits 1 (`stable stream consumer group(s) still
  have active members after 20s`): a SIGKILLed loader stays a group member until the 45 s session timeout. The docs' default (session timeout + 5 s) is right; a
  supervisor must not shorten it. The soak uses 60 s; every B8 restart therefore costs about a minute.
* **The documented recovery filter is unsafe on a shared engine.** `docker ps -a --filter label=app=graph-loader` matched all 11 containers of the soak's fleet (labels
  `app=graph-loader`, `component`, `run_id`, `edge_type`, `replica_id`); `docker rm -f $(... -aq --filter label=app=graph-loader)` would remove any other graph-loader
  fleet on the engine. The soak never runs it: recovery removes containers its observer adopted on the owned network, re-verified as owned, by recorded ID
  (`Fleet.finish`, `soak.cleanup`). Docs finding for BULK_LOAD.md 13 / INCREMENTAL_LOAD.md B10: add `--filter label=run_id=<id>` (stream) as the first recipe.
* Stream node containers are auto-removed, so their logs vanish: `LogCollector` follows every container while it lives. Node rejections are logged by
  `(topic, partition, offset)`, not by `rid`: the accounting matches malformed node records by location (`rejections/*.jsonl` under the run directory).
* The CLI's own ephemeral port: `GRAPH_LOADER_METRICS_PORT` is passed per fleet; container metrics are on their own mapped loopback ports (read from the label
  `graph_loader.metrics_port` and the inspect port map).
