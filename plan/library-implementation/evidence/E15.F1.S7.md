## Behaviour

* **Selection**: `GRAPH_LOADER_LOG_FORMAT=json` or `--log-format json`, read before argument parsing (anywhere on the command line, any command: it is removed from argv before argparse). Roles inherit the choice through the same environment variable (Docker: passthrough only when set; process runtime: the role environment), so the parity trace is unchanged.
* **Text mode** (the default): `configure_logging` is exactly the old `logging.basicConfig(level=INFO, format="%(levelname)s: %(message)s")`, installs no hook, patches nothing, and for the two entrypoints that never configured logging (`retry_consumer`, `clock_runner`) does nothing at all. Proven byte-identical: record fixtures through the formatter (with and without structured extras); the full output (exit code, stdout hash, stderr) of five real invocations equals the output recorded from the previous source (`tests/golden/text_logs_1211283.json`, produced by running them against `git archive 1211283` and checked equal to this tree before the change); `schema-example`, `validate-schema`, `--version` and `start --help` stdout are identical in both formats.
* **JSON mode**: one JSON object per line on stderr with `ts, level, logger, execution_id, run_id, kind, name, replica, incarnation, stage, message`, then the structured fields of the event. Identity comes from the S2 environment keys (`GRAPH_LOADER_EXECUTION_ID`, `GRAPH_LOADER_INCARNATION`), `GRAPH_LOADER_RUN_ID` and `set_log_context(kind, name, replica)`. The envelope can never be overwritten by a field. Credentials (URL passwords, `password=`/`token=` pairs) are redacted from the message, the fields and tracebacks.
* **Structured fields at emission**: `structured("<stage>", field=...)` as `extra=` at every call site of the documented stages (`runtime`, `metrics-ready`, `node-label-ready`, `node-write`, `edge-write` (three sites), `edge-plan-rejections`, `bulk-substage` / `bulk-substage-complete` (seven), `outcome`, the six write-outage lines) and `StageLogger("retry-consumer")` for the DLQ retry consumer (all of its lines). A static test walks every logger call of the code base and fails when a documented stage has no structured fields; all other messages carry `message` only. No `key=value` parsing anywhere.
* **Uncaught exceptions** (main thread and other threads), **argparse errors** and `warnings` go through the same handler (process-wide patch of `ArgumentParser.error`, `sys.excepthook`, `threading.excepthook`, JSON mode only); a `SystemExit("message")` becomes one error line and exit status 1 (`run_entrypoint`).
* **Early SIGTERM** (node loader, before the heavy imports): standard library only; a JSON line in JSON mode, the old bytes otherwise.
* **Children** (process runtime): the roles write JSON on their own; the relay passes a child's JSON line through UNCHANGED and wraps stray non-JSON output (a `print`, a traceback) as one JSON object (`stage: child-output`); the CLI's own stderr lines (OOM report, hook failures, dropped relay lines) and `_child.py`'s messages follow the format; planner workers (spawned) configure JSON logging from the inherited environment.
* **Payloads are never touched**: `schema-example` YAML, `validate-schema` output, `status --json`, `--help`/`--version`, the Docker preflight's stdout protocol.

## librdkafka

Messages reach the application only when a client is polled (checked on confluent-kafka 2.5.3 and 2.16.1: zero records before a poll, hundreds after). In JSON mode `utils/kafka_logging.install()` replaces `confluent_kafka.Consumer` and `Producer` by subclasses and wraps `AdminClient.__init__` in place (it cannot be subclassed: its `__init__` refers to its own module-global name); modules of this package that already bound `Consumer`/`Producer` by name (the entrypoint modules do, at import) are rebound, so install order does not matter, and EVERY factory, module-level or deferred import, passes `"logger"`. Draining: clients their owner polls (subscribed or assigned consumers, producers with delivery callbacks) are left to the owner; metadata-only consumers, admin clients and callback-free producers are polled with `poll(0)` by one daemon thread every 0.5 s and drained once more on `close()`/`flush()`. The disposition of each factory (including the metadata-only consumers of `bulk_monitor.py`, `relationship_bulk_monitor.py`, `planned_edges.py`, `status/lag.py`) is the table in the module docstring, and a drift guard fails when a construction site is added without a line there (16 files, 48 call sites).

**Guard (orchestrator, accepted):** this process-global patch of a third-party module happens ONLY inside this package's own entrypoint processes (`configure_logging`, which the CLI, every role and the planner workers call) and ONLY in JSON mode. `import neo4j_graph_loader`, the supported library API (`neo4j_graph_loader.schema`, `planning`) and the logging/Kafka helper modules never install it, even with `GRAPH_LOADER_LOG_FORMAT=json` set or `--log-format json` in argv: `test_importing_the_package_and_its_library_api_never_touches_confluent_kafka_even_with_json_logging_set` asserts `confluent_kafka.Consumer`, `Producer` and `AdminClient.__init__` are the originals after importing both. `Consumer.close()` and `Producer.flush()` drain once, so a short-lived consumer or producer keeps its last lines; an `AdminClient` has no `close()` and a one-shot one that lives under 0.5 s can still lose lines: documented limit for S13.

## Not covered / notes

* The Docker runtime's roles were not run in a container here (no Docker); live container JSON lines are an S12 cell on the host.
* A one-shot Kafka client that lives under 0.5 s may log nothing (documented); consumers and producers their owner polls log when the owner polls (a stuck owner delays its own client's lines).
* `--log-format` is documentation in the parser (the value is consumed before parsing); the Python API (`neo4j_graph_loader.*` as a library) does not configure logging at all, as before.
