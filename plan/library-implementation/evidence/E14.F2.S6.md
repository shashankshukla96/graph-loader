## What was built

- `orchestrator/cgroup_budget.py` (new, **process backend only**). `read_view()` reads the CLI's cgroup v2 chain (`/proc/self/cgroup`, then `memory.max` / `memory.current` at the leaf and every ancestor up to the root).
  Sizing formula (documented in the module docstring and below):

      headroom = min( MemAvailable, min over the leaf and every visible ancestor with a finite memory.max of max(0, memory.max - memory.current) )
      reserved = CLI 200 MiB + sum of the role peaks (node 150, edge 150, planned writer 150, dispatcher 120, lease server 100, retry consumer 150, clock 100)
      planner  = max(0, headroom - reserved) x 0.8
      workers  = requested, reduced to floor(planner / 256 MiB) when the 256 MiB floor of every worker does not fit; per worker = min(4096, planner / workers)

  Refusals (`SizingError`, `stage=sizing reason=...`, exit 1, **before any role is launched**): not even one 256 MiB worker fits; explicit `--plan-workers` x `--plan-memory-mb` need more than `planner`; a limit file exists but cannot be read (or neither a limit nor MemAvailable can be read) and the two planner settings were not both given explicitly.
- `ProcessService.apply_plan_budget(args, schema)` stores the result in `args.plan_workers` / `args.plan_memory_mb` and logs `stage=sizing planner_workers= planner_memory_mb= headroom_mb= reserved_mb= planner_mb= roles= [note='planner concurrency reduced from N to M ...']`; the CLI calls it (process backend, planned mode) right before the planner starts.
- **Docker mode is untouched**: `edge_planner.available_memory_bytes()` / `default_plan_memory_mb()` and every planner default are exactly as before; `docker_service.py` does not reference the new module.

## Live cells (Linux host; no container, no image: a systemd user scope)

**Priority change (user, via the orchestrator): process-based execution comes first, so the limited cells run WITHOUT a container.** The CLI runs inside a transient systemd **user scope** (`systemd-run --user --scope --unit=e14-<owner8>-<cell> -p MemoryMax=<n>M -p MemorySwapMax=0`) on the host: the user manager is reachable over SSH (`XDG_RUNTIME_DIR=/run/user/1000`, `systemd 255`, `State=active`, the memory controller is delegated to it). The scope is the CLI's cgroup, so `cgroup_budget` reads a real finite `memory.max` on the leaf and `systemd` ancestors above it. The product runs with no Docker at all (`DOCKER_HOST=unix:///nonexistent/e14-no-docker.sock`); the only containers are the owned Neo4j/Kafka test infrastructure, reached over loopback (same stack, image pins and guards as the S4 matrix; user-approved throwaway containers). Per-cell sampling every 0.5 s of the scope (`memory.current`, `memory.peak`, `memory.events`) and of each process's `VmHWM`; a host `MemAvailable` breach below 1.5 GB would stop the CLI through its normal stop path (SIGTERM through the verified registry pidfd). Final run: `logs/limits-scope.log`, **4 passed in 38.8 s**.

**Stated margin of the formula:** every reserved role size is at or above that role's measured peak (asserted); the formula's total is at or above the measured peak (asserted) and at most 3x the measured peak plus 700 MiB (asserted; measured: 3.1x - deliberately conservative: the reserves are per-role *peaks* and the 120-relationship fixture does not stress the planner).
**What the cells do not show:** a workload large enough that the *unbounded* default would have exceeded the limit; the refusal control (8 x 1 GiB cannot fit) and the computed budget show the mechanism; a data-volume stress belongs to the S10 soak.

That image was removed by ID and **no image is built any more for S6**; the container variant is not part of the evidence set.

## Notes for docs / later stories

- Sizing guidance for the docs: required memory ~= `CLI 200 + sum(role peaks) + planner (workers x >= 256 MiB)`; the per-role table above is the measured basis; with no readable limit give `--plan-workers` and `--plan-memory-mb`.
- Roles are reserved by schema replicas (`node.replicas`, default 1); bulk auto-replicas (derived from topic sizes) can add node loaders after sizing - a run that scales beyond the reserve is bounded by the cgroup limit itself (an OOM kill is then reported at group level, S8).
