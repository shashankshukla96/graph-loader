**Priority.** P1, directly after E14 and before the release candidate is frozen (the release waits for E14 and E15:

it is a later epic (E16, after the release) unless the user decides otherwise.

**Outcome.** A user can follow any run — bulk or stream, Docker or process runtime, host, single container, systemd or
Kubernetes — with their own tools:
1. a versioned, machine-readable **run status and event history in a configurable store**: either JSON files in the
   run directory or a SQL database (PostgreSQL supported, SQLite for single-host use), read with `graph-loader status`
   or a Python accessor;
2. **JSON logs** from the CLI and every role;
3. **monitoring that works outside the bundled stack**: dashboards and alert rules that run on the user's own Prometheus
   and Grafana with any discovery (Docker, file, Kubernetes, static), configurable datasource, intervals, thresholds and
   labels, installed with the package;
4. the bundled local Prometheus + Grafana stack kept as a quick start, with safe defaults.

**Why (verified 2026-11-02, corrected by Codex round 1).**
- `graph-loader status` lists node-loader containers only (bulk and stream), with no phase, progress, lag, relationship
  types or errors, and only in Docker mode (`cli.py:3081`).
- Progress is spread across `key=value` text logs, per-process `.prom` snapshots, `stage-*.json`/`substage-*.json`
  timing files, the planned-edge ledger and the dispatcher's STATUS/SUMMARY; no single document says what a run is doing.
- Monitoring assets live only in the checkout (`monitoring/`); the wheel ships none of them, and the artifact verifiers
  reject both extra resources and `Provides-Extra` (`plan/library-implementation/tools/verify_e03_artifacts.py:22,64`,
  `scripts/verify_installed.py:362`).
- `run_id`, `node_label`, `edge_type`, `writer_id`, `replica_id` reach Prometheus only as **target labels relabelled from
  Docker labels**; ordinary series carry only entity labels (`utils/metrics.py:254`) and `graph_loader_process_info`
  carries `kind`, `name`, `version` (`utils/metrics.py:744`). The dashboard and the alert files use `run_id`; without
  Docker SD some alerts break, others lose run isolation or annotations.
- The dashboard pins datasource uid `prometheus`; the scrape interval (3 s) is hard-coded; Grafana defaults to
  `admin/admin` with anonymous viewer and both UIs bind `0.0.0.0`.
- E14 writes a `file_sd` file for process mode, but its per-child ephemeral ports are not reachable for a Prometheus in
  another pod or host.

**Scope.** Product (`src/`), packaging (package data and optional extras, with the artifact contract and validators
updated), docs, tests, `monitoring/`, `docker-compose.monitoring.yml`, `Makefile`. Not in scope: checkpoint/resume (E16),
webhooks or a push bus (users ship events and JSON logs with their own shipper), OpenTelemetry export, real-cluster
Kubernetes testing.

**Prerequisites.** E14 complete. During E14 only dashboard/alert **drafting against mock data** may proceed; final queries
wait for S8's identity contract.

**Exit gate.** The live status/events/logs matrix (S12) passes for every start mode in both runtimes including failures;
dashboards and alert rules pass firing/non-firing fixtures and an external Prometheus/Grafana proof with file, static and
Docker discovery; the Kubernetes wiring is rendered and validated (real cluster excluded); the bundled stack works;
base, `[sql]` and `[postgres]` installs pass the updated artifact gates; docs quick starts run from a fresh wheel.

## Decisions

D15-1, D15-2, D15-3 and D15-5 accepted as recommended by the user on 2026-11-02 ("I accept"); D15-4 decided by the user.

- **D15-1 Contract stability.** **Recommended:** the status model, event schema, SQL read schema and the documented
  metric names/labels are public, versioned (`schema_version`) and changed only additively within a major version.
- **D15-2 Bundled stack defaults.** **Recommended:** bind `127.0.0.1`, Grafana admin password required at start-up (not at
  shutdown), anonymous access opt-in.
- **D15-3 Process-mode metrics exposure.** **Recommended:** the CLI serves one aggregated `/metrics` on a configurable
  fixed port (`--metrics-port`, needed for Kubernetes Service/PodMonitor wiring) that merges its own and every child's
  registry; per-child endpoints stay available through `file_sd`.
- **D15-4 Status store — decided by the user** ("use PG, which can be configured"; "Either json or a sql db"):
  `--status-store {json,sql}`, one active store per run. SQL through SQLAlchemy Core and a database URL; PostgreSQL
  (psycopg 3) tested and supported, SQLite tested for single-host use, other dialects allowed but untested. SQL support is
  optional (`[sql]`, `[postgres]` extras); the base install gains no dependency.
- **D15-5 Event delivery guarantee.** **Recommended:** durable local outbox (below): every event is on local disk before
  it is acknowledged internally; the SQL store receives it at least once and deduplicates; bounded storage, and any loss
  beyond the bound is recorded as an explicit gap.

## Design

### Identity

- **run_id** — the logical run (today's `--run-id` or generated); may be reused (the soak supervisor restarts with the
  same id; relationship phases derive sub-ids, `cli.py:1183`).
- **execution_id** — a UUID created as the first act of every `graph-loader start` (before schema load, so start-up
  failures are recorded); one per CLI process. Phase sub-ids are recorded as `phase_id` children of the execution.
- **incarnation** — a UUID per role process start (container or child), so a restarted role is distinguishable.
- Status rows, events and metric exporters are keyed by `execution_id` (and `incarnation` for roles), never by `run_id`
  alone.

### Status model and sources

Overall `state` (`starting`, `running`, `stopping`, `succeeded`, `failed`, `stopped`) plus **activities** that overlap
(`planning`, `nodes`, `edges`, `draining`, `stream`), each with its own state and timestamps — no serial phase sequence.
Every numeric field is `{value, observed_at, source}` or `null` (unknown); a missing or failed observation is never 0.

| Field | Source (all modes unless stated) | Semantics |
|---|---|---|
| node `records_written` | roles' periodic metric snapshots (below) summed per label | at-least-once write count, not distinct records |
| node `ready` | node monitor control messages (`bulk_monitor.py:283`) | bulk only; stream: n/a |
| relationship `records_written` | edge/writer snapshots per type | at-least-once loader writes; retry-consumer writes reported separately as `retry_written` |
| `retry_written`, `retry_redlq`, `retry_parked` | **new** retry-consumer outcome counters (today one callback mixes them, `retry_consumer.py:3228`) | at-least-once outcome counts |
| relationship `lag` | CLI lag poller (`relationship_bulk_monitor.py:834`) | `null` after a failed poll, never the stale value |
| node `lag` | **new** node-loader consumer-lag gauge with an observation timestamp (not emitted today) | `null` until first observed |
| plan chunks `done/total` per type | planned ledger + dispatcher SUMMARY (`planned_dispatcher.py:192`); live global STATUS only as a run-level total | planned bulk only |
| `rejected` | planner totals (exact once planning ends); **new** `graph_loader_rejected_total{kind,name}` counter in node, classic and lease edge paths | planner: exact; others: observed rejection events (at-least-once), not a durable distinct count |
| `dlq_lag` | retry consumer `dlq_backlog` = high watermark − committed offset (`retry_consumer.py:402`) | unprocessed DLQ records; carries its own `observed_at` because a failed calculation keeps the previous value (`retry_consumer.py:2885`) |
| `parked_size` | parked topic high − low watermark | physical retained topic size, not unresolved logical records |
| roles | runtime handles (E14) | state, incarnation, restarts, exit code, last error |

**Snapshots as the transport.** The CLI reads the roles' atomic metric snapshots (Docker bind-mounts the timing
directory and preflight checks it, `docker_service.py:189`, `_docker_preflight.py:85`; process mode shares the
filesystem). For status they change as follows:
- written to `<timings>/<execution_id>/<incarnation>/metrics-*.prom`, listed in a per-execution manifest, so executions
  sharing an explicit timing directory never collide;
- every gauge that can go stale has a companion `*_observed_at_seconds` gauge set only on a successful observation; the
  CLI uses it, never the file's modification time, so a fresh file with a stale value is reported as stale;
- when a status store is active, snapshots are written at the status interval (default 5 s) even if the HTTP metrics
  endpoint is disabled; with snapshots impossible (read-only directory) the fields are `null` with a reason;
- a total across incarnations is the sum of each incarnation's last snapshot; if an incarnation ended without a final
  snapshot (SIGKILL), the total is marked `lower_bound: true`, never silently reset.

S2 implements the reader and the new instrumentation and documents every field per mode, including "not applicable".

### Stores

**Selection.** `--status-store {json,sql}` / `GRAPH_LOADER_STATUS_STORE`, default `json`. The attempt directory (today's
`<run-dir base>/<random>`, `_runtime.py:55`) always gets a small `status-locator.json` naming the store, the
`execution_id`, the run id and, for SQL, the database URL **without credentials** and the schema, so any reader starting
from the run directory finds the data.

**JSON store.** `status.json` (atomic temp + rename on every change, at most every N s) and `events.jsonl` (one object per
line: `schema_version`, `execution_id`, `seq` (per execution, gap-free), `ts`, `type`, fields). Rotation keeps up to K
files of S MB; readers iterate across rotated files; deleted history is reported as a gap.

**SQL store.** Configuration: `GRAPH_LOADER_STATUS_DB_URL` (SQLAlchemy URL; PostgreSQL password may come from
`PGPASSWORD`, `.pgpass` or a service file), `GRAPH_LOADER_STATUS_SCHEMA` (default `graph_loader`, ignored on SQLite),
driver TLS parameters. Tables: `executions` (PK `execution_id`; run id, versions, host, mode, runtime, timestamps,
state, outcome, exit code, `heartbeat_at`, `revision`), `execution_activities`, `execution_labels`, `execution_types`,
`execution_roles` (PK `execution_id, role, replica, incarnation`), `execution_events` (PK `execution_id, seq`, JSON
payload, payload hash), `schema_version`. A snapshot is written as **one transaction** carrying a monotonically
increasing `revision`; an older revision is rejected. Inserting an event whose key exists with a different payload hash
is an error (reported, metric), never silently ignored. Migrations: `graph-loader status-store migrate`; `start` refuses
an older schema with a clear error unless `--status-store-auto-migrate`. Retention: `status-store prune --older-than`
deletes finished executions only. Only the CLI connects; roles never receive the URL. The password never appears in any
output.

**Durable outbox (SQL store, D15-5).** An event gets its `seq` only when it is appended and `fsync`ed to
`<attempt>/status-outbox/` (small batches, at most B ms); that is the **durable acknowledgement**. The guarantee covers
durably acknowledged events: they are delivered at least once and deduplicated. Events still in the in-memory batch
window when the CLI is killed have no `seq` and are lost; the docs state the window. Delivery trims acknowledged
records. Bounds: on overflow, undelivered *snapshots* are dropped first (only the latest matters); then a contiguous
range of events is replaced by a `gap` record with its `seq` range and counts, written durably **before** the covered
records are deleted. If the outbox itself cannot be written, the store is marked degraded (metric, one log line), no
exact gap is claimed, and the execution is flagged `history_incomplete` when the database is next reached. A per-attempt
lock (`flock`) serializes the live writer, an automatic recovery at the next `start` and any `graph-loader status-store
flush --run-dir <attempt>`; torn tails are truncated to the last complete record; recovery resolves the destination
from the locator and credentials from the environment, never from the outbox. Shutdown waits for delivery up to a
deadline, then leaves the outbox for recovery. Loads are never blocked by the store.

**Readers.** `graph-loader status [--run-dir <attempt|base>] [--execution-id <id>] [--json] [--watch] [--refresh-lag]`
and `status --list [--active]`. Exit codes: `0` running or succeeded, `1` failed, `2` stale/unknown, `3` stopped.
**Stale** = no heartbeat/update within a threshold; **dead** only when E14's registry proves the CLI process is gone on
this host. `--refresh-lag` does one bounded Kafka query (timeout) and never blocks otherwise. Python:
`neo4j_graph_loader.status.read_status(...)`, `iter_events(..., follow=False)` for either store, typed and schema-validated.

### JSON logs

`--log-format {text,json}` / `GRAPH_LOADER_LOG_FORMAT`, read before argument parsing. A shared `configure_logging()` is
called first in every entrypoint: CLI, node loader (including its early SIGTERM handler, which today writes text to
stderr, `node_loader.py:17`), edge loader, planned writer, planned dispatcher, lease server, clock runner, retry
consumer, planner workers (spawned entrypoint), E14's `_child` wrapper. librdkafka logs are routed through the
confluent-kafka `logger` setting into Python logging for every Kafka client factory (Producer, Consumer, AdminClient);
callbacks are only delivered when the client is polled, so each factory documents how its log callbacks are drained
(existing poll loops; a periodic `poll(0)` only for clients the code owns and that hold no subscription or
assignment; metadata-only consumers, `relationship_bulk_monitor.py:108`, are listed explicitly with their handling), and
the route is tested on the minimum supported confluent-kafka (2.5) and the current one; uncaught exceptions and argparse errors go through the configured
handler. In JSON mode every line of the designated log streams (stderr, and stdout of long-running roles) is one JSON object (`ts`, `level`, `logger`,
`execution_id`, `run_id`, `kind`, `name`, `replica`, `incarnation`, `stage`, `message`, plus structured fields). Structured
fields are attached **at emission** for the documented stages (`runtime`, `metrics-ready`, `node-label-ready`,
`node-write`, `edge-write`, `edge-plan-rejections`, `bulk-substage*`, `outcome`, outage/DLQ stages) through a helper;
other messages carry `message` only — no parsing of `key=value` text. E14's relay passes JSON lines through unchanged
(children already carry identity) instead of adding a text prefix. Command payloads are not logs and keep their format in
both modes: `schema-example` YAML, `validate-schema` results, `status --json`, help/version output and any internal
protocol on stdout. Text mode stays default and is proven unchanged with deterministic log-record fixtures.

### Metrics identity and exposure

Every exported sample carries `run_id`, `execution_id`, `exporter` (unique per role incarnation, e.g.
`node-Person-r1-<incarnation8>`) and `runtime` as **metric labels**; these names are reserved and `--extra-labels`
rejects them. Constant identity labels add no within-exporter expansion, so **active** series per live exporter do not
grow; but historical series now split per execution and incarnation where today some targets reuse addresses or names
(`MONITORING.md:133`). S8 budgets by exporter starts within the retention window (active series and retained churn
separately, including the new health families) and tests repeated executions.
Dashboards and rules aggregate on these labels directly — **no `group_left` joins on `process_info`** — so historical and
absence queries (the one-hour deadlock evidence, `concurrency.yml:9`; the absent-DLQ alert, `dlq.yml:94`) keep their
current behaviour after an exporter disappears. Docker SD keeps working. Every exported scrape configuration sets `honor_labels: true`.

**Scrape health and isolation.** Each discovery mode has exactly one authoritative scrape path: per-child targets
(Docker, file) or the aggregated endpoint (static/Kubernetes for the single container), never both; `monitoring export`
generates one, and a shipped rule flags duplicate observations of the same `exporter` from two jobs. Health: per-child
targets carry portable target labels (`exporter`, `run_id`, `execution_id` via Docker relabelling or `file_sd` labels)
so `up` identifies them; the aggregated path uses `graph_loader_exporter_up{exporter}`; dashboards and the health alert
use `up` or `exporter_up` according to the configured path (S9 rewrites the existing `up` panel, dashboard line 308).
Matching on `instance` (e.g. `progress.yml:43`) becomes matching on `exporter`; absence and history rules group by
`execution_id` (not the reusable `run_id`).

Aggregated endpoint (process mode, D15-3): merges the CLI's registry and each child's scrape; one HELP/TYPE per family;
samples are unique because `exporter` differs; a child's series disappear when it exits (Prometheus staleness), and a
restarted child is a new `exporter` (counter reset handled by `rate()`). Scrape health per child is exported as
`graph_loader_exporter_up{exporter}` (Prometheus `up` covers only the aggregate target); a failed child scrape omits that
child's series for that scrape and sets its `exporter_up` to 0.

### Portable bundle

Assets move to package data (`neo4j_graph_loader/monitoring/`); the checkout's `monitoring/` equals them (test).
`graph-loader monitoring export --out <dir>` with `--discovery {docker,file,kubernetes,static}`, `--scrape-interval`,
`--job-name`, `--extra-labels`, `--metrics-port`, `--values alerts.yaml` writes: a scrape-config snippet; Kubernetes
`Service` + `PodMonitor`/`ServiceMonitor` for the aggregated port (single container, E14); alert rules from values
(defaults reproduce today's thresholds and firing outcomes) with generated promtool tests; dashboards with Grafana
`__inputs`, a datasource variable and `$__rate_interval`; a PostgreSQL run-history dashboard with its own datasource
input.

**Bundled stack.** Uses the exported bundle; D15-2 defaults; `make monitoring-up` validates the password,
`make monitoring-down` never needs it (scoped stop/remove as today).

## Risks to watch

- Identity labels on every sample: confirm no dashboard or alert silently changes its grouping.
- Outbox disk use on long outages (bounded; measured in S5).
- Changing the bundled stack's defaults surprises existing local users (changelog note).
