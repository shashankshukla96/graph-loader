# E01 — Decide the alpha release contract

Plan review: **approved**. Implementation: **complete**.

**Outcome.** A signed-off decision record that downstream stories can implement without inventing product choices.

**Scope.** Recommended first scope: schema validation, producer relationship planning and installed CLI; no new embedded fleet API. Defaults are proposals until the user chooses.

**Prerequisites.** None; may begin with the current checkout.

**Exit gate.** D01–D07 are resolved and recorded by the user; any broader API, stronger ordering guarantee or unsupported platform choice triggers plan revision and independent re-review before dependent work.

Epic prerequisites apply to every story, in addition to the story-specific dependencies below. Estimates are rough focused engineering effort, not elapsed-time commitments. Story completion requires its acceptance criteria, validation, and evidence; implementing a file alone is insufficient.

### Story E01.F1.S1 — Resolve distribution and executable identities

- Status: complete; estimate: 0.5 engineering day(s).

- Change surface: decisions.md D01; proposed distribution/import/CLI identities; ownership record.
- Evidence: `../evidence/E01.F1.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Check normalized PyPI/TestPyPI name collisions and executable collisions, recording dates and evidence.

### Story E01.F1.S2 — Resolve API, ordering and compatibility promises

- Status: complete; estimate: 1 engineering day(s).
- Checklist: S2, S3, V7.
- Story dependencies: E01.F1.S1.
- Change surface: decisions.md D02/D03; schema/plan/chunk/DLQ/index/group compatibility table.
- Evidence: `../evidence/E01.F1.S2.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. List supported public imports, exceptions, return/input types and CLI modes; identify internal modules.
2. Choose alpha maturity/version policy and deprecation rules across Python APIs and persisted/wire formats.
3. Document restart, rebalance, 100,000-entry LRU eviction, cross-topic offsets, manual replay and replica limits; choose explicitly restricted guarantees or revised implementation scope. Producer planning requires Kafka.
4. D02 explicitly resolves the proposed cancellation/deadline/error surface and process-versus-inline limits in cancellation-contract.md before E04; a broader guarantee requires re-splitting/review.
5. D02 also resolves the complete-frame transport and codec-boundary clauses in cancellation-contract.md; poll readiness alone is not an acceptable bounded-receive implementation.

**Validation**

- Review the API/format table against schema.py, edge_plan.py, retry_consumer.py and consumer_groups.py.
- User approves D02/D03. If stronger durable/order guarantees or embedded ingestion are chosen, split and review new epics before treating this story as done.

## Feature E01.F2 — Environment and distribution choices

### Story E01.F2.S1 — Resolve support matrix and extra boundaries

- Status: complete; estimate: 1 engineering day(s).
- Checklist: S4, D2, D3.
- Story dependencies: E01.F1.S2.
- Change surface: decisions.md D04/D05; import/dependency inventory; environment matrix.
- Evidence: `../evidence/E01.F2.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Choose interpreter, OS and architecture support separately for schema/planner APIs and CLI/container operations; Python 3.12/Linux is the proposed starting point.
2. Map each proposed extra to actual eager imports; base dependencies remain mandatory until separation is implemented and tested.
3. Choose Rust mandatory/optional policy, matching Neo4j-driver constraint and pure-driver behavior; record Kafka/Neo4j server versions, Enterprise/APOC requirements.

**Validation**

- Inventory requirements.txt and imports in CLI, planner, schema, metrics and Neo4j code.
- Approve minimum/current dependency sets and the full advertised support matrix; justify any Python upper bound with an incompatibility.
