- **D19-3 Registry setting.** **Recommended:**
  - `GRAPH_LOADER_IMAGE_REGISTRY=<prefix>` makes every default reference `<prefix>/graph-loader-<role>:<version>`.
  - The prefix grammar is separate from the full-reference regex: `host[:port](/path-component)*` with lowercase path
    components. It rejects a scheme, userinfo (`@`), a tag or digest, whitespace and empty components, before any
    logging.
  - The four `GRAPH_LOADER_<ROLE>_IMAGE` variables still win. Their existing regex additionally rejects userinfo (a
    tightening of an operator input that was never documented to carry credentials).
  - It applies wherever images are used (Docker runtime roles, the single-container CLI image); the process runtime
    ignores it.
  - Unset, behaviour is unchanged apart from the namespace.
- **D19-4 Self-built images through BuildKit.** **Recommended:**
  - `graph-loader images build --registry <prefix>` builds the four images for the installed package version **from
    the released package itself**.
  - It drives `docker buildx build` (BuildKit), a documented external prerequisite. It fails closed with a clear message
    when `buildx` is missing.
  - The Docker SDK cannot pass BuildKit secrets, so it is not used for builds. The SDK stays in use for everything
    else; there is no new Python dependency.
  - The build context is generated in a fresh temporary directory from package data shipped in the wheel and sdist: the
    four Dockerfiles and the D19-5 lock files.
  - Each image installs the exact package wheel and its locked dependencies with `--require-hashes --only-binary=:all:`,
    from one of two sources:
    - `--pip-index-url <url>`: the org's PyPI mirror, without credentials; or `--pip-index-secret <file>`, a file whose
      only content is the index URL, which may carry credentials. This is the **one** supported secret format, with no
      pip config files and no netrc. The file is mounted as a BuildKit secret;
    - every install runs through a small shipped helper (`install.py`, run with `python -I`). The helper reads the secret
      file itself and starts pip with a **fresh environment** containing only `PATH`, `PIP_CONFIG_FILE=/dev/null` (no
      global, site or user config file is loaded) and `PIP_INDEX_URL`. The URL never appears in any process's argv, in
      image history or in a layer. It runs with `--no-cache-dir`, no extra index and no inherited `PIP_*` or proxy
      variable. Round-3 controls showed that `pip --isolated` still loads global and site config files, and that
      `--index-url "$(cat ...)"` puts the secret in argv; both are therefore rejected designs;
    - `buildx` and the push run with a sanitized environment:
      - no `*_PROXY` and no predefined proxy build arguments, unless the user passes `--proxy` explicitly;
      - a fresh `DOCKER_CONFIG` holding a named context and builder, plus **scoped registry authentication**: only the
        `auths`, `credHelpers` or `credsStore` entries for the base-image registry and the target registry, copied from
        the user's Docker config (or from `--docker-config <dir>`). No other registry, proxy or plugin setting is
        copied. The credential helpers must be on `PATH`;
      - registry credentials are never logged, never written to the manifest and never put into the build context;
    - an internal index with a private CA: `--pip-ca-bundle <file>` (not a secret) is copied into the context, and the
      helper sets `PIP_CERT` to it;
    - before installing, the helper runs `pip config list` in the same fresh environment, and the output must be exactly
      the expected `:env:` keys (`config-file`, `index-url`, and `cert` when a CA bundle is given), with no file values.
      The two-key case was verified locally with planted site and user `pip.conf` files and `PIP_EXTRA_INDEX_URL`;
    - `--wheelhouse <dir>`: offline, `--no-index`; the directory is checked against the lock before the build starts.
  - `--base-image` (default `python:3.12-slim`) points at the org's mirror. It is resolved to a digest before the
    build, and the Dockerfiles build `FROM` that digest.
  - `--debian-mirror <url>` rewrites the apt sources for the `tini` install. A base image that already carries `tini`
    0.19.0 skips apt.
  - Tags are `<prefix>/graph-loader-<role>:<version>` with the three labels the CLI checks.
    `org.opencontainers.image.source` stays the public repo.
  - Without `--push` no image is pushed. `--push` pushes with `docker push` under the same sanitized `DOCKER_CONFIG`,
    so build pulls and pushes share one credential path. The Docker SDK is not used for pushes.
  - The command builds for the daemon's own platform only.
  - **The release images are built through the same path**: the candidate builder passes the candidate wheel and a
    wheelhouse, adds its suffix and writes its manifest. The evidence contract is extended explicitly, not assumed
    (D19-6).
- **D19-5 Hashed per-platform locks.** **Recommended:**
  - A complete, hashed dependency lock per supported target: CPython 3.12 on Linux amd64 and Linux arm64.
  - It is generated by a dev-only tool run in a matching Linux container. It is not a base dependency; the story picks
    `pip-compile --generate-hashes` or `uv pip compile --generate-hashes`, whichever produces binary-only closures for
    both platforms.
  - It replaces the ranges in today's image installs, so the **Python dependency set** of an image is reproducible.
    Whole-image byte reproducibility is not promised: Debian package revisions come from the mirror at build time
    (`Dockerfile:6` already states this limit). The manifest records the base digest and the installed Debian package
    versions. The package's own metadata ranges in `pyproject.toml` are unchanged.
  - `requirements.txt` stays the generated range list for developers. The lock files are new package data and are
    refreshed by a `make lock` target with a `--check` mode in CI-style tests.
  - Wheelhouse preparation runs **inside the target base image on the matching platform**:
    `docker run --platform linux/<arch> <base> pip download --only-binary=:all: --require-hashes -r <lock>`, plus the
    package wheel. It is not `pip download --platform manylinux2014_<arch>` on another machine: today's
    `confluent-kafka` and NumPy wheels are `manylinux_2_27`/`_2_28` and are rejected under `manylinux2014`
    (`var/e11-validation-20261101/images-amd64/cli-build.log:32,42`).
    - amd64 is prepared on the Linux host, arm64 on the Mac.
    - The documented command is tested against the chosen locks on both platforms.
    - Dependencies are never downgraded to fit a platform tag.
- **D19-6 Image provenance contract.** **Recommended:**
  - Every build (candidate or user) writes a manifest with:
    - recipe version, Dockerfile hashes, base image digest;
    - the exact package wheel file name and sha256;
    - the lock file sha256 and every dependency artifact sha256;
    - the build arguments, minus secrets;
    - the resulting image ids and references.
  - The installed runner, `installed_service.py` and the service-lane preflight consume these fields. The source-file
    hash comparison is replaced by wheel-hash binding.
  - Adversarial controls:
    - a substituted wheel of the same version;
    - a changed Dockerfile or lock;
    - a wrong-platform wheel in the wheelhouse;
    - a missing dependency wheel with no fallback.
- **D19-7 Export, quarantine and guard.** **Recommended:** a private tool
  `plan/library-implementation/tools/export_public.py`.
  - **Quarantine.** Every export is prepared in a fresh scratch clone of `Neburyx/graph-loader`, outside both
    repositories, whose only parent is the last approved public commit (none for the first). Steps:
    1. materialize the allowlisted files of a named private commit as a **full replacement tree**, so files absent from
       the new manifest are deleted;
    2. run the guard on the tree;
    3. only then commit with the D19-1 identity and a user-approved message;
    4. re-run the guard on every newly reachable commit, tree and the commit metadata;
    5. print the file list, the diff against the last public snapshot and the proposed reference.

    A failure deletes the quarantine clone; no public branch or tag moves. Pushing is a separate step that needs the
    user's instruction each time. A private mapping file records private commit → public commit.
  - **Exact-tree validation.** The materialized public tree (not the private tree with folders deleted) runs:
    collection, the Mac unit suite, the artifact verifier, the doc-link check and the installed-runner checks.
    - **Before the freeze** (S8), these run with development artifacts built from that tree, to prove the tool.
    - **For a release** (After E19, step 5), they run again on the frozen commit's export, and its product-file hashes
      must equal the frozen wheel and sdist payload. This is a release step, not an E19 acceptance.
  - **Public tags** are created only on the validated public snapshot, never transferred from the private repo. The
    runbook tags the public commit.
  - **Guard, fail closed:**
    - Git entry types: only regular files with mode 100644 or 100755. Symlinks, gitlinks, submodules and nested `.git`
      are rejected.
    - Text files must be UTF-8.
    - Binary files are allowed only by exact path and sha256 from a reviewed list; anything else is rejected,
      including archives.
    - Path and filename checks run on every entry.
    - Denylist, case-insensitive:
      - AI tool and agent words: `claude`, `codex`, `anthropic`, `openai`, `gpt-`, `subagent`, `cartographer`,
        `.agents`, `.claude`, `co-authored-by`;
      - internal-plan pointers `plan/(v[0-9]|library-implementation|[a-z0-9-]+\.md)`, which does not match product
        identifiers like `graph-loader-edge-plan/1`;
      - RFC 1918 addresses;
      - `/Users/` and `/home/` paths;
      - email addresses other than the public contact and the noreply address;
      - credential patterns:
        - private-key headers;
        - `AKIA[0-9A-Z]{16}`;
        - `gh[pousr]_[A-Za-z0-9]{36,}` and `github_pat_`;
        - `pypi-AgE`;
        - `xox[abpr]-`;
        - `-----BEGIN`;
        - URL userinfo;
        - `password|secret|token` with a quoted literal value;
      - the actual secret values of the private credential files, read at run time from their 0600 files, compared
        by hash and never printed.
    - Allow-entries are exact (path + line sha256 + reason), reviewed, never directory-wide. Example: the privacy
      assertions in tests that mention `/home/`.
    - Commit author and committer must be the D19-1 identity, with no trailers.
    - Every proposed annotated tag is checked too:
      - the tagger must be the D19-1 identity;
      - the message must pass the denylist;
      - the peeled target must be a validated public commit, with only public ancestry.
  - **Limits stated in the guide:** a denylist cannot prove absence (paraphrase, encodings, images). The user reviews
    the printed file list and diff before every push.
- **D19-8 Proof environment — approved by the user on 2026-11-03.** **Topology:**
  - **Network.** One owned Docker network created with `--internal` on the shared daemon, which has no route off the
    host. Owned services on it:
    - `registry:2` with htpasswd authentication, as `registry:5000`. The base image is stored there, so every build
      performs an authenticated private `FROM` pull;
    - `pypiserver` with basic auth, behind an owned TLS proxy, as `https://pypi:8443`. Its certificate is from an owned
      throwaway CA, trusted only through `--pip-ca-bundle` in the build and through the runner image's CA store. Plain
      HTTP is never used, because pip ignores an HTTP index without a trusted-host exception;
    - a static file server holding a flat Debian repository with only `tini` and its dependencies, as `debian:80`.
  - **Inner daemon.** An owned, privileged `docker:dind` container (pinned version) on that network, with:
    - its own empty image store on an owned volume;
    - `--insecure-registry registry:5000` in its own daemon arguments (the shared daemon is not changed);
    - its unix socket in an owned volume.
  - **Runner.** An owned runner container on the same internal network, from a runner image built before isolation
    (`python:3.12-slim` by digest, the Docker CLI and the `buildx` plugin, the package from the wheelhouse). It runs
    `graph-loader`:
    - `DOCKER_HOST=unix:///run/dind/docker.sock`: a local socket, so the real preflight
      (`_docker_preflight.py:22`) stays enabled and passes;
    - the work directory as a volume mounted at the **same absolute path** in the runner and the inner daemon, so the
      preflight's shared-writable-path check (`:85`) passes;
    - a fresh `DOCKER_CONFIG`, no proxy variables, and a named `buildx` builder on the `docker` driver of the inner
      daemon. Builds therefore run in the inner daemon's BuildKit and load straight into its image store, with no
      container-driver builder and no export step;
    - Dockerfiles with no `# syntax=` line, so no frontend image is pulled.
  - **Load services.** Neo4j 5.26 and Kafka run **inside** the inner daemon, from images pulled from the owned registry,
    on an inner user-defined bridge network that the CLI uses with `--network`.
  - **Seeding.** One seeding phase through the shared daemon, before isolation: pull by digest, then push to the owned
    registry, build the runner image, fill the index and the Debian repo. It is the only step with public access.
  - **Isolation controls.** Each boundary gets a denied-public control and a successful internal equivalent, run in four
    places: the runner, the inner daemon (a pull), a build `RUN` step and a role container.
    - Denied: TCP connect to a public address, and pulls from `docker.io`, `ghcr.io`, `pypi.org` and `deb.debian.org`.
      These must fail with a **network** error (unreachable, refused or timeout), not an authentication error, a
      missing image or a DNS answer alone. DNS may resolve on internal networks, so transport denial is what counts.
    - Allowed: the same operation against the owned registry, index and repo succeeds.
  - The shared daemon's configuration, the host firewall, DNS and the user's services are never changed.
  - Removal is by recorded container, network and volume ids; everything inside the dind daemon goes with its volume.
  - Budget: 10 GB disk, 8 GB memory in total (dind, Neo4j and Kafka inside it), 4 CPUs; the host memory guard
    applies.
  - Alternative: a machine or VM the user provides with no internet access.

  - **Amendment 2026-11-03 (S5, implementer):** the docker driver allows no named builder instance (`docker buildx create --driver docker` fails with
    "additional instances of driver "docker" cannot be created"). The builder is therefore the implicit `default` builder of a fresh `DOCKER_CONFIG` whose

## Design

### Namespace and identity (S1)
- One constant per place: `ghcr.io/neburyx` and `https://github.com/Neburyx/graph-loader`.
- Tests read the package constant **and** keep one independent literal assertion of the Neburyx contract, so a wrong
  constant fails.
- The frozen `docker_parity_0.1.0a1.json` and old evidence stay as they are. Its retained comparison test normalizes
  exactly the image namespace (a namespace-only change fails the comparison today), and that normalization is itself
  tested.
- `docker_parity_0.1.0a2.json` is regenerated with the diff limited to the namespace.

### Cutting the code's ties to `plan/` (S2)
- **Moves:**
  - `run_e04_fault.py` → `tests/fixtures/run_fault.py`;
  - `verify_e03_artifacts.py` → `scripts/verify_artifacts.py`;
  - `check_doc_links.py` → `scripts/check_doc_links.py`.
- **Inventory migration, not a byte copy:**
  - The producer emits **portable** paths: repo-relative, with no private collection or artifact paths. Private
    provenance (hosts, paths, run logs) goes to a private sidecar that stays in `plan/`.
  - The public file `tests/inventory/test-inventory.json` is re-frozen with a migration step. It compares every existing
    id, disposition and order against the baseline and fails on any loss, reorder or disposition change. Path and hash
    fields are allowed to change, and are listed.
  - Doc edits keep yaml-fence line positions, so the literal frozen snippet ids survive. If positions must move, content
    anchors may **map to the existing legacy id strings**, but they never rename them (additions-only rule). A control
    proves an attempted rename is rejected.
- The installed lanes and the stage copy in `verify_installed.py:68,78` accept the new paths only.

### Build (S4–S6)
- **Dockerfile build arguments:**
  - `BASE_IMAGE`;
  - `DEBIAN_MIRROR`;
  - the wheel and lock paths inside the context;
  - a pip install step through `install.py` with a fresh environment and `PIP_CONFIG_FILE=/dev/null`, reading the index
    URL only from the BuildKit secret (`--mount=type=secret,id=pip_index`) or the plain `--pip-index-url`, or
    `--no-index` with the wheelhouse.
- No credential is ever a build argument.
- The `tini` version check is unchanged.
- **Default builds** reproduce today's labels, entrypoints and user. The installed distribution set changes only from
  ranges to the locked pins, which the S5 comparison lists.
- **Credential tests:**
  - a sentinel credential is absent from argv, the build context, the logs, the image configuration and history,
    every layer tarball and the manifests;
  - with `PIP_EXTRA_INDEX_URL`, `PIP_INDEX_URL`, a global `pip.conf`, a user `pip.conf` and `*_PROXY` all planted in
    the client environment and in the base image, the install still uses only the intended source. This is proven by
    the owned index's access log and by a planted fallback index that is never contacted.
- **`graph-loader images build` options:**
  - `--registry`, `--tag-suffix` (development only);
  - `--base-image`, `--pip-index-url` or `--pip-index-secret`, or `--wheelhouse`;
  - `--proxy` (explicit only), `--docker-config <dir>` (the source of the scoped registry logins), `--pip-ca-bundle`;
  - `--debian-mirror`, `--push`;
  - `--dry-run` prints the plan and builds nothing;
  - `--output <dir>` writes the D19-6 manifest;
  - `--replace` is required to overwrite an existing tag.
- **Refusals:** a version that is not the installed one, a bad prefix, a missing `buildx`, or a wheelhouse that does
  not satisfy the lock.
- The artifact contract's resource list grows by exactly the Dockerfiles and lock files (finite list kept). Both artifact
  validators and the installed runner's payload allowlist are updated with controls.
