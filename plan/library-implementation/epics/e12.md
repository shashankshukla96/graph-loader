# E12 — Authorize production and establish maintenance

Plan review: **approved**. Implementation: **not started**.

**Outcome.** A separately approved public release, verified retrieval and actionable recovery procedure.

**Scope.** No publishing, tags/commits pushed, deployment or account changes occur under this planning task. Future execution needs the concrete approval gates below.

**Prerequisites.** E11

**Exit gate.** Production install and real load match the approved candidate; release/recovery/support records are complete and no gate is silently waived.

Epic prerequisites apply to every story, in addition to the story-specific dependencies below. Estimates are rough focused engineering effort, not elapsed-time commitments. Story completion requires its acceptance criteria, validation, and evidence; implementing a file alone is insufficient.

## Feature E12.F1 — Production gate and exact publication

### Story E12.F1.S1 — Review the evidence and obtain production authorization

- Status: planned; estimate: 0.5 engineering day(s).
- Checklist: R1.
- Story dependencies: E11.F2.S2, E10.F2.S2.
- Change surface: Completed checklist/evidence index; explicit exclusions and N/A rationale; user release instruction.
- Evidence: `../evidence/E12.F1.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. All B/S/P/A/D/V/U and applicable T gates have evidence; no unresolved broad-scope branch is hidden behind an N/A.
2. Present exact files/hashes, clean commit/tag, image digests, support/ordering limits and rollback plan.
3. Require explicit user approval for PyPI publication and any Git/image pushes; independent plan approval alone is never execution approval.
4. Link the completed E10.F2.S2 release and recovery runbook; do not request approval using a future post-release task as the rollback plan.

**Validation**

- Human reviews the concrete release manifest and completed gates; record the instruction without copying secrets.

### Story E12.F1.S2 — Publish the verified bytes and references

- Status: planned; estimate: 0.5 engineering day(s).
- Checklist: R2.
- Story dependencies: E12.F1.S1.
- Change surface: PyPI upload; approved release tag/reference; image digest references.
- Evidence: `../evidence/E12.F1.S2.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. For file versioning create the local release tag at the tested commit; SCM mode reuses the pre-build candidate tag. Push only references expressly authorized by the user.
2. Ensure compatible approved image digests are available and upload the exact rehearsed wheel/sdist bytes to PyPI.
3. If any source/artifact/image changes, stop publication, create a new candidate and repeat validation/rehearsal as required.

**Validation**

- Compare SHA-256 manifest immediately before explicit-file twine upload; verify tag resolves to the tested commit and record returned index files.

## Feature E12.F2 — Public verification and recovery

### Story E12.F2.S1 — Verify the public release and publish release records

- Status: planned; estimate: 1 engineering day(s).
- Checklist: R3, R4, R5, U5.
- Story dependencies: E12.F1.S2.
- Change surface: Fresh PyPI install evidence; release notes/compatibility references; actual-version installation guidance; Actual released version/URL/image references filled into the E10.F2.S2 runbook; next dependency-review owner and cadence.
- Evidence: `../evidence/E12.F2.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Download exact version from normal PyPI, compare hashes and run pip check/API/CLI smoke plus a small real load.
2. Check project-page metadata and record compatible image digests, maintainer contact and test results.
3. Update external docs/release records to actual version without silently changing the already uploaded package bytes.
4. Fill the actual release URLs, version and image digests into the E10.F2.S2 runbook without altering uploaded bytes; record the next dependency-review owner and cadence.
5. Actual yanking, deletion or user-data migration still needs a separate specific instruction; maintenance grants no standing destructive authority.

**Validation**

- Fresh unrelated environment, provenance checks and isolated load; record all outcomes and only claim release completion on success.
