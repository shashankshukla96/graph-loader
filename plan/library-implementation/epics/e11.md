# E11 — Freeze and rehearse a release candidate

Plan review: **approved**. Implementation: **not started**.

**Outcome.** Immutable artifact and image evidence plus a separately authorized TestPyPI rehearsal.

**Scope.** This epic includes future external actions only as gated stories. The current planning request and earlier no-push instruction authorize none of them.

**Prerequisites.** E10

**Exit gate.** Exact candidate wheel/sdist bytes, image identity, ownership, page inspection and retrieved-install checks are recorded; failures trigger a new candidate and revalidation.

Epic prerequisites apply to every story, in addition to the story-specific dependencies below. Estimates are rough focused engineering effort, not elapsed-time commitments. Story completion requires its acceptance criteria, validation, and evidence; implementing a file alone is insufficient.

## Feature E11.F1 — Candidate ownership and immutable artifacts

### Story E11.F1.S1 — Confirm accounts and configure the selected publisher

- Status: planned; estimate: 0.5 engineering day(s).
- Checklist: T1, T2, T3.
- Story dependencies: E10.F2.S1.
- Change surface: Release ownership/publisher records; non-secret configuration; conditional automation branch.
- Evidence: `../evidence/E11.F1.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Verify separate PyPI/TestPyPI access, email/security requirements, maintainers and project ownership/name.
2. For manual Twine, document the controlled environment and external token handling; add no workflow.
3. Only if the user explicitly changes policy: configure both pending/registered Trusted Publishers with exact owner/repo/workflow/protected environment, separate publish job and id-token: write; otherwise T3 is N/A.

**Validation**

- Check account/publisher settings without exposing credentials; record authorized human responsibilities and any required user actions.

### Story E11.F1.S2 — Freeze source/version and build the exact package candidate

- Status: planned; estimate: 0.5 engineering day(s).
- Checklist: P3, V1, V2, V3, V4, V5, V6, T4.
- Story dependencies: E11.F1.S1.
- Change surface: Clean release snapshot; explicit artifact inventory; SHA-256 manifest; local image identities.
- Evidence: `../evidence/E11.F1.S2.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Freeze all scoped source, requirements, resources and package release notes at a clean reviewed candidate snapshot. Include formerly untracked prerequisite files in that source identity.
2. For SCM mode create the local candidate tag before all final builds; file-version mode records the tested candidate version/commit. No Git push is authorized.
3. Build wheel/sdist in an empty candidate directory, inspect/twine-check and record exact filenames/hashes, metadata and version. Do not reuse development build bytes by assumption. Final image construction and full attestation follow in S3/S4.

**Validation**

- python -m build; python -m twine check --strict on explicit candidate files; inspect inventories, metadata/license/version/entrypoints and private-file exclusions.
- Rebuild/install the sdist wheel without .git and validate version/resources. Record the source/dependency/build-input manifest for S3/S4.

### Story E11.F1.S3 — Build final component images/context from the frozen candidate

- Status: planned; estimate: 1 engineering day(s).
- Checklist: D4, P3, V6, T4.
- Story dependencies: E11.F1.S2.
- Change surface: Final component image/context builds; immutable source/dependency/version manifest.
- Evidence: `../evidence/E11.F1.S3.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Build every shipped component from the exact frozen E11 source/version and reviewed dependency inputs, preferably installing the frozen wheel; source-copy builds must prove equivalent source/version injection. Never carry forward E06/E09 development image IDs as final proof.
2. Assert package metadata, Python version API, executable --version, metrics version labels and image compatibility metadata agree according to the approved override policy. Record source commit/tag, wheel hash where installed, dependency/build-context hashes, local image IDs/OCI archive hashes.
3. For bundled context, verify the exact context packaged in the final wheel/sdist, build all supported components from it and record identities; a registry push is not required for that branch. Any source/version/context/dependency change invalidates the relevant artifacts/images and S4 evidence.

**Validation**

- Build and start every final component with version/import/help checks; inspect labels and capture actual in-image runtime/dependency identities.
- Compare to final package version/manifest; mark old development-image evidence superseded and prohibit substitution in upload/approval commands.

### Story E11.F1.S4 — Attest final packages and matching images together

- Status: planned; estimate: 1 engineering day(s).
- Checklist: V1, V2, V3, V4, V5, V6, T4.
- Story dependencies: E11.F1.S3.
- Change surface: Final candidate evidence bundle; matrix/service runs bound to exact wheel/sdist/image/context hashes.
- Evidence: `../evidence/E11.F1.S4.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Run E07 wheel and sdist-built-wheel isolation/provenance checks and E08 support lanes against the final package bytes.
2. Run E09 supported-mode/order/failure gates using the final E11.F1.S3 image identities or final bundled-context builds. Earlier development-image service passes are not the final gate.
3. Produce one immutable manifest linking source/tag/version, package filenames/hashes, tested component IDs/context hashes and all gate evidence. Later changes require a new candidate and repeated affected plus final gates before publication.

**Validation**

- Execute the installed runner lanes and matrix/service gates using explicit manifest paths and final component identities; inspect actual package/CLI/metrics/image versions.
- Verify no artifact comes from a stale dist directory or an older image tag; preserve all pass/skip/exclusion reasons.

## Feature E11.F2 — Authorized external rehearsal

### Story E11.F2.S1 — Obtain approval and publish candidate images/TestPyPI files

- Status: planned; estimate: 0.5 engineering day(s).
- Checklist: D4, T4.
- Story dependencies: E11.F1.S4.
- Change surface: Explicit user publication instruction; exact artifact/image manifests; release command record.
- Evidence: `../evidence/E11.F2.S1.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Present the concrete version, commit, files/hashes, image targets and test results; obtain a new explicit user instruction for the specific image and TestPyPI uploads.
2. If prebuilt registry delivery was selected, push only the validated images after authorization and record registry digests; verify content identity against local candidates.
3. Upload exactly the manifested wheel/sdist bytes to TestPyPI; preserve no-push until specifically superseded and never infer PyPI production permission.
4. Only the frozen S4 manifest is uploadable. For bundled-context delivery, skip registry publication with the D06 rationale; TestPyPI still requires its explicit instruction.

**Validation**

- Use explicit image targets and explicit twine upload --repository testpypi <candidate-wheel> <candidate-sdist> after authorization.
- Re-pull images by digest and verify compatibility/content; changed image contents require renewed validation.

### Story E11.F2.S2 — Verify retrieved artifacts and index presentation

- Status: planned; estimate: 1 engineering day(s).
- Checklist: T5, T6, V2, V6.
- Story dependencies: E11.F2.S1.
- Change surface: TestPyPI download/hash record; isolated install results; rendered project-page checklist.
- Evidence: `../evidence/E11.F2.S2.md` (create when executing, exclude secrets).

**Acceptance criteria**

1. Retrieve the exact candidate version with --no-deps from TestPyPI, then install the reviewed dependency set from normal PyPI separately; never combine indexes via --extra-index-url.
2. Compare retrieved hashes; run pip check, public API/CLI/resource checks and a small real load using the published candidate images.
3. Inspect README/license/links/Python support/maintainers/files; defects require a new version/candidate and repeated affected gates.
4. Production release and E12 consume the frozen S4 manifest plus verified registry digests (prebuilt strategy), or the validated bundled context; never substitute development images.

**Validation**

- Download/install into a fresh virtualenv and unrelated cwd; record hashes, provenance and real-service result.
- Capture project-page checks; do not treat a no-deps install or skipped Docker test as full proof.
