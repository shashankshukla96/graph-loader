# E17 — Native Windows process launcher (later)

Plan review: **not planned in detail; backlog placeholder.** Implementation: **not started; deferred until after the
first release.** Recorded 2026-11-02 at the user's request ("Add a windows native launcher mechanism for later part. Not
right now").

**Outcome.** `graph-loader start --runtime process` runs natively on Windows (no WSL2, no Docker), with the same
supervision guarantees E14 proves on Linux, plus a documented Windows service shape.

**Why later.** E14 deliberately limits process mode to Linux (D14-2). A native port touches the shutdown path of every
role, which E09/E13 test hardest, so it is kept out of the first release.

**Expected scope (to be planned and reviewed before work starts).**
- A stop mechanism that does not depend on POSIX signals for all seven roles and the planner workers (preferred: a
  `stop` message on E14's control channel; `CTRL_BREAK_EVENT` as fallback).
- A Windows backend behind E14's `Runtime`/`Handle` protocols: process handles instead of pidfds, Job Objects for groups,
  memory limits and kill-on-CLI-death, process creation time for identity, `SetProcessAffinityMask` for `LOADER_CPUSET`.
- Cross-platform file locking for the run registry and E15's outbox (no `flock`).
- A Windows service shape (documented wrapper such as NSSM, or a built-in service).
- Test-suite portability (POSIX-only tests split or skipped with a Windows counterpart), a Windows soak, and a D04
  support-matrix decision.

**Prerequisites.** First release shipped (E12); E14 and E15 complete; a Windows test machine reachable by the agents
(OpenSSH server, Python 3.12, Docker Desktop or WSL2 for throwaway Neo4j/Kafka).

**Rough effort.** About 8–12 hours of AI-agent time (15–25 human engineering days by the plan's sizing), dominated by
role shutdown and test portability.

**Interim answer for Windows users (first release).** WSL2 (process mode runs there unchanged); optional, not yet tested.
